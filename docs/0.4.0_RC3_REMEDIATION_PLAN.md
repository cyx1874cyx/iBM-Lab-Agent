## 4. P0：锁定必须成为服务端硬门禁

涉及文件：`lib/synthesis.js`、`lib/remote.js`、相关集成测试。

### 4.1 统一写保护

所有修改既有路线或路线证据的入口，第一步必须读取路线并调用统一的 `assertWritable`。至少补齐：

- `updateRouteStatus`
- `addStepEvidence`
- `collectEvidence`
- 所有新增的批次、结构、步骤、审核和 Agent 回写入口

允许的唯一例外是“复制为新版本”：它创建新 ID，源版本保持只读，新版本默认 `locked=false`。

不要依赖前端 disabled；应直接调用服务方法验证锁定后拒写。

### 4.2 只有用户可以锁定

当前 `lockRoute(id, { by })` 会信任调用方字符串。应改为可信调用上下文或明确角色参数，并在服务端验证主体是用户；`by: "agent"`、缺失身份、伪造字符串均不得锁定。

如果当前架构暂时没有可信身份对象，应缩小远程接口：

- UI 使用专门的 user-action 调用通道。
- Agent 工具层不暴露锁定方法。
- 服务端仍保留显式角色校验，禁止仅靠按钮隐藏。

### 4.3 审核批次状态

统一“运行中批次”的定义。UI 当前把 `pending/applied` 都视为 open，而锁定服务只检查 `pending`。建议：

- `pending`：等待 Agent；阻止锁定。
- `applied`：Agent 已回写、等待下一轮人工审核；阻止锁定，直到批次完成且新事实全部决定。
- `completed`：关闭，不阻止锁定。

锁定时同时检查 `pending` 和 `applied`，避免 UI 与服务端语义不一致。

### 4.4 必须新增的集成测试

- locked 路线拒绝新增 Evidence。
- locked 路线拒绝改变路线状态。
- locked 路线拒绝开放数据回写。
- locked 路线拒绝步骤、结构、审核、批次和 Agent 回写。
- `by=agent` 不能锁定；可信用户可以锁定。
- `pending` 和 `applied` 批次均阻止锁定。
- 复制 locked 路线得到新 ID，且新版本可写、源版本不变。

## 5. P0：截图事实核验必须验证“实际可见”

涉及文件：`lib/evidence-shot.js`、`lib/synthesis.js`、`client/index.js`、Evidence 模型和测试。

当前 `evidenceShotable` 只检查 `bundleId/documentId + page`。这不能证明 PDF 存在、页码有效或截图成功。

### 5.1 推荐实现

为 Evidence 增加可追溯截图核验状态，例如：

```text
shotVerification.status = pending | ready | failed | stale
shotVerification.bundleId
shotVerification.page
shotVerification.sourceDigest
shotVerification.renderedAt
shotVerification.error
```

截图服务成功生成后才登记 `ready`。原 PDF、页码、bbox 或文件摘要变化后状态必须变为 `stale`。

### 5.2 前端门禁

- 截图仍在 loading、失败、缺文件、页码越界或状态 stale 时，“确认”不可点击。
- 右侧截图成功显示后，才允许依据它确认左侧事实。
- “修正”不得绕过首次截图审核。若原文确实不可用，应选择“无法确认”并交给 Agent，而不是把无截图修正直接当作完成。
- 错误区必须显示可行动原因：缺原文、页码错误、渲染器缺失或文件损坏。

### 5.3 服务端门禁

- `reviewEvidence(..., confirmed/corrected)` 必须验证对应截图状态为 `ready`。
- `lockRoute` 再次验证所有需要原文依据的最终事实均为 `ready`，不能相信客户端状态。
- 截图失败后，即使有 `bundleId + page` 也必须阻止确认和锁定。

### 5.4 测试

- 元数据存在但文件不存在：不能确认。
- PDF 存在但页码越界：不能确认。
- 渲染失败：不能确认和锁定。
- 截图成功：可以确认。
- 原 PDF 被替换后原确认变 stale，重新核验前不能锁定。

## 6. P1：化合物双源与 CAS

涉及文件：`src/synthesis/compound-resolve.js`、`src/chemistry/rdkit-pubchem.js`、模型和测试。

### 6.1 结构一致性

禁止直接比较原始 SMILES 字符串。先通过 RDKit 或等效化学工具规范化，再比较 canonical SMILES 或 InChIKey：

1. 两源结果分别规范化。
2. 优先比较标准 InChIKey；没有时比较规范化 canonical SMILES。
3. 规范化失败应返回 `unresolved` 或明确错误，不能误判一致。
4. 保存两源原始值、规范化值、查询时间和来源 URL/ID。

新增测试必须覆盖：芳香环大小写、支链顺序、盐形式、立体化学、相同结构不同 SMILES、真正冲突。

### 6.2 PubChem CAS

当前 PUG property 请求不返回 CAS。名称查询成功后，应再查询 PubChem synonyms，并从可验证的同义词中筛选符合 CAS 校验和的编号。

CAS 校验不能只检查正则格式，还要验证校验位。保存：

- `casNumber`
- `casSource`，例如 `pubchem-synonym`
- 对应 PubChem CID
- 查询时间

如果无法确认 CAS，界面显示“CAS 待确认”，不得把化合物名称误当 CAS。

### 6.3 超时与降级

PubChem 和 CACTUS 请求分别设置超时并独立记录失败。一个源超时不能无限阻塞整个步骤；单源候选仍必须用户点击确认后才能写入。

## 9. P0：优化 Windows 运行时准备

涉及文件：`desktop/scripts/prepare-runtime.ps1`、`desktop/scripts/build-windows-release.ps1` 和脚本测试。

### 9.1 当前问题

`Get-TreeMetadataDigest` 使用递归枚举、`Sort-Object` 和完整 `$rows` 集合。大目录下会产生高 CPU、高内存和长时间无输出。本次构建曾达到约 2.7 GB 工作集；最终没有进入验证和 NSIS 阶段。

### 9.2 修复要求

- 插件源码优先用 `git ls-files` 获取稳定清单；对未跟踪但允许打包的明确目录单独加入。
- 流式向增量 SHA256 写入相对路径、长度和时间，禁止构造完整 `$rows` 与大字符串。
- DSH 指纹只依赖锁文件、入口包版本和解析后的依赖闭包，不递归扫描整个 `node_modules`。
- Node 指纹只哈希选定 `node.exe`。
- 每个组件指纹单独计时并即时输出阶段日志。
- 删除与复制分别输出开始、结束、耗时和目标。
- 快照未变化时必须跳过删除和复制。
- 刷新时先写到同盘临时目录，验证通过后原子切换；不要先删除最后一个可用快照。
- 失败或进程被终止时清理本次临时目录；锁文件使用独占句柄判断，不能仅凭文件存在判断活跃。

### 9.3 性能验收

在当前 Windows 机器上记录冷/热两组数据：

- 热构建：三组件均未变化，应在 30 秒内结束 `prepare-runtime`。
- 仅插件变化：不得复制 DSH/Node。
- 仅 DSH 锁变化：不得复制插件源码。
- 指纹阶段峰值内存目标小于 500 MB。
- 每 20 秒心跳必须显示真实子阶段，而不只是总进程 CPU。
