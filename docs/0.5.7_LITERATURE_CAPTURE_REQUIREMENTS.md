## 4. 需求详述

### R1 访问通道策略：闭源直走机构，仅已知 OA 社探测

**目标**：把"OA 优先"从"每篇都试"改成"只对已知有 OA 供给的出版社试"，其余出版社直接进机构通道。

**现状**：捕获链路**没有** OA 判定；`lib/literature-sources.js` 的检索链路有完整实现（OpenAlex → 候选 PDF → 文件级校验 → 失败回落机构），可直接复用其判定与校验逻辑。

**改法**

1. 出版社规则表增加字段 `oaProbe: boolean`（`lib/tasks-tool.js:72-81` 的 `PUBLISHER_RULES`）。**初始集合**：`nature`、`springer`（两者已是 `directSi: true`）。其余六家 `oaProbe: false`。
2. 通道选择顺序（结果写入 `accessMode`）：

```
iWAN 全部路由可用        → iwan   （OA/非 OA 均直连，与现状一致）
未启 iWAN，且 oaProbe     → 先探测 OA：命中 → oa（Node 侧无凭据抓取）
                                    未命中 → webvpn（需登录则先请用户登录）
未启 iWAN，非 oaProbe     → 直接 webvpn（不再发任何 OA 请求）
不需要机构的公开 SI       → direct（现状保持）
```

3. OA 探测规则（复用既有经验，不新造轮子）：
   - 只用 OpenAlex `works/https://doi.org/<doi>` 取候选位置，**只取 `pdf_url`，不抓 HTML**；
   - 最多 5 个候选，单个超时 ≤ 15 s，整体预算 ≤ 30 s；
   - 必须过 PDF 文件级校验（`%PDF-` 头 + 尺寸 + ≤250 MiB，复用 `validatePdfBuffer`；见 R14）；
   - **任何一步失败都不阻断机构路径**（沿用 `lib/literature-sources.js:689` 的纪律）；
   - 结果按 DOI 缓存（进程内即可），避免同一篇反复探测。
4. 新增 `accessMode = "oa"`，并在归档 provenance 里记录实际通道（`open-access` / `institutional-iwan` / `institutional-webvpn`）。

**安全边界**：OA 抓取是 Node 侧 `fetch`，**不带任何 Cookie/票据**，不读 WebView2 profile；这是本方案引入的唯一 WebView2 之外的出网路径，需在代码注释与手册里显式声明。

**验收**

- 闭源 DOI（如 `10.1016/…`）在无 iWAN 时，日志与状态中**不出现** OpenAlex 请求；
- 已知 OA 社的 OA 命中用例：`accessMode=oa`、归档 provenance 为 `open-access`；
- OA 未命中的已知 OA 社用例：**自动**回落机构通道，任务不停在中间态；
- 断网/OA 服务 5xx：走机构通道，日志记一条 `oa-probe-failed`，任务不失败。

**风险**：OpenAlex 会把"bronze OA / 出版社自有 pdf_url"列为 OA，那类仍需机构会话。→ 所以 OA 只能是加速分支，永不作为阻断闸门。

### R2 通路收敛：B 退出

**目标**：正文采集以“下载事件（A）”与“CDP Fetch（C）”为正式路径，删除连续约 10 个 beta 版本实测不可用的响应层 `GetContent` 取体（B）。

**现状**：B 与 C 并存，且**共用同一套载荷机制**（`ensure_pdf_payload` / `finish_pdf_segment` / `*.payload.pdf`）。B 独有 `Content-Range` 分段装配（`webvpn.rs:3855-3920`），C 只接受 `200 + application/pdf` 的完整正文（`webvpn.rs:3607-3624`）。

**改法**

1. 删除 B 的**取体**部分：`WebResourceResponseReceived` 处理器不再调用 `GetContent`，不再做 206 分段装配。
2. **保留** B 的**事实观察**：主文档 `content-type / status / content-length` 仍由 `WebResourceResponseReceived` 上报——`deriveCaptureView` 的 `page.documentType`、`httpStatus`、`contentLength` 与 `documentType=application/pdf → download-viewer-pdf` 的判定都依赖它。
3. `pdfPayload`（`ready/complete/contentLength/receivedBytes/error`）机制**保留**，其字节载荷仅由 C 写入；先核对 `payloadVerdict` 各分支的实际调用后再清理，不凭名称删除仍在使用的诊断。
4. 手册同步：`docs/LITERATURE_DOWNLOAD_CHAIN.md` §3 的"两条字节通路"表改成 A/C，并删掉 206 装配段落。

**必须明说的后果**：删除 B 会移除 `206 / Content-Range` 分段装配能力。代码中确有 Wiley 等站点的 Range 请求记录，因此**不能写成“实测中该场景不出现”**。用户已确认 B 长期不可用，故仍按 D3 退役；遇到只有 206、C 无法取得完整 200 PDF 的页面时，走 A 的真实下载入口或人工保存，并记录站点、DOI 与失败码。若 A 也不可用，须如实报“未取得完整 PDF”，不得拼接不完整文件或登记成功。

**验收**

- 在浏览器默认 PDF 页上，以 0.5.6 已验证的 CDP Fetch 行为为回归基线：`pdfFetch` 日志出现“已捕获原请求 PDF（N 字节）”，`pdfPayload.complete=true`，随后可归档；出版社定制预览页的下载入口走 A；
- 抓包/日志中不再出现 `GetContent` 调用；
- 页面事实（documentType/httpStatus/contentLength）与改造前一致（用 `lab_browser_debug` 比对）；
- 用一个已观察到 Range 请求的站点验证：A 可取得完整文件，或给出明确的人工接管与未完成状态；
- Rust 单测：删除 B 的用例，C 的完整性用例保留并通过。

**通路 D**：`ShowSaveAsUI` 不作为自动获取路径；保留人工兜底入口及必要诊断，待人工保存回归通过后再评估代码清理。

### R3 归档冲突：已有文件 → 明确失败 + 小球「已有文件」

**目标**：目标条目已有该类型文件时，**不得静默覆盖**；归档必须失败，且失败原因对人和 AI 都可读、可处置。

**现状**：静默覆盖。`saveCapturedFile` 写 `.tmp-*` 后 `rename`，失败则 `rm` 目标再 `rename`（`lib/manual-capture.js:830-838`）；`registerCapturedFile` 直接覆盖 `pdfPath/pdfSha256`（`lib/tasks/literature.js:570-589`）。唯一痕迹是 sha 变化会作废旧证据截图。

**0.5.7 改法：先做到不可覆盖且提示一致**

1. 建任务前按 `{projectId,bundleId,kind}` 预检。若已有文件或登记路径，**不建任务**，返回 `archiveConflict{kind,fileName,size,sha256,archivedAt}`、`code=already-archived`、`requiresUserAction=true`。面板/小球显示独立的 `conflict` 提示“已有文件”；此时**没有**可转为 `failed` 的任务。可执行选项只有“保留原文件/取消”；替换与分件删除随 0.5.8 的 R5 一起开放。
2. 已建任务在上传时遇到冲突：归档端点是最终权威，写目标文件之前再次核对磁盘和条目登记，并按 `{projectId,bundleId,kind}` 串行化冲突检查与登记。返回 HTTP 409、`code=already-archived`，任务转 `failed`，`reasonCode=already-archived`；此时小球也显示 `conflict`。上传暂存文件按明确的清理策略处理，原件及其登记绝不改变。
3. 移除“rename 失败就先 `rm` 目标再重试”的覆盖分支。默认无覆盖授权；Agent 不能通过自填布尔参数绕过检查。

**0.5.8 扩展：人工决定替换**

在 R5 分件管理可用后，面板提供“替换/保留/取消”。替换由宿主记录一次性、绑定 `{projectId,bundleId,kind,existingSha256}` 的人工确认凭据；`allowOverwrite` 布尔值**不能单独作为授权**。旧文件保留一份带 sha 的备份，备份名冲突不得覆盖；先确保新文件完整且可验证，再做替换与登记，失败时回滚到旧文件和旧登记。provenance 记录新旧 sha、操作者、时间和关联任务。备份应提供明确恢复入口，不能以“永远换得回来”代替验收。

**验收**

- 预检冲突：未建任务、未触发下载，独立 `conflict` 提示可见；状态工具不虚构 `failed` 任务；
- 上传时冲突及并发双任务：最多一个归档成功，另一方 409；旧文件字节与登记在失败路径不变；
- Agent 直接传 `allowOverwrite=true` 或伪造普通请求，仍不能覆盖；
- 0.5.8 替换用例：人工凭据仅可使用一次；新文件校验失败、重命名失败、登记失败时旧文件可恢复且 provenance 与最终状态一致；
- `tests/unit/capture-closed-loop.test.mjs` 增补上述 0.5.7 冲突回归。

### R4 归档错误码体系

**目标**：归档失败必须能让 AI **决定下一步**（而不是只看到一句中文），并且能原样展示给人。

**改法**：在既有 `code` 回传机制（`lib/manual-capture.js:199-222`）上收敛出一张固定表，工具状态里原样暴露 `reasonCode` 与出错阶段 `stage`，并标明是否可重试：

| `code` | 含义 | 建议处置 |
| --- | --- | --- |
| `bundle-missing` | 条目不存在 / 不属于本课题 | 不要重试；告诉用户条目已失效 |
| `already-archived` | 该类型已有文件（R3） | 0.5.7 保留原文件并停止；0.5.8 可由人选择替换/删除 |
| `kind-mismatch` | 实际文件类型或下载入口与任务类型不符 | 核对文件内容与入口，重新选择正确类型 |
| `invalid-pdf` | 头/尾/大小校验不通过 | 换入口（`retry-download-entry`） |
| `too-large` | 超过 250 MiB（R14） | 停止本次归档，向用户报告实际大小与上限；仅在取得完整、校验通过的文件后才能登记 |
| `token-expired` / `token-replayed` | 令牌过期/重放 | 重建任务 |
| `task-not-armed` | 任务尚未就绪或已终态仍在操作 | 读取当前任务状态；终态须重建任务，不能复用旧令牌 |
| `storage-failed` | 写盘 / rename 失败 | 报错给用户，附路径 |

**验收**：每个 code 至少一条单测；状态工具的 `message` 必须同时给出 code、stage、可重试性与可执行建议；任何错误都不得把未校验载荷登记为已归档。

### R5 分件删除（PDF / SI / 精读报告 / PPT）

**目标**：条目可以只删某一类产物，用于修正"人工归档错了"这类情况。

**现状**：只有 `lab_tasks_delete_bundle`（整条删，含报告与 PPT，要求 `confirm=true`），见 `lib/tasks/entry-admin.js:286-331`。

**改法**

1. 服务层新增 `deleteBundleArtifact({ projectId, bundleId, artifact, confirm })`，`artifact ∈ {pdf, si, report, ppt}`：
   - `pdf` → 删 `bundle.pdfPath`，清 `pdfPath/pdfSha256/acquisitionStatus`；
   - `si` → 删 `bundle.siPath`，清 `siPath/siSha256`；
   - `report` → 删该 bundle 的 report 行与其文件（`report-md` / `report-docx` / `report-contract`）；
   - `ppt` → 删 presentation 行与其文件（`ppt` / `ppt-contract` / `ppt-conformance`）。
2. 文件定位以各行实际登记的路径为准；`literatureEntryLayout` + `entryFileName`（`lib/entry-layout.js:270-293`）只用于核对预期位置。对每条实际路径执行课题工作区内的严格越界检查，拒绝目录逃逸与符号链接逃逸；报告/PPT 的关联文件逐项列清。
3. 新工具 `lab_tasks_delete_bundle_file(bundleId, artifact, confirm)`；`confirm=true` 只是防误触参数，**不等于人工同意**。Agent 发起不可逆删除时，须经面板人工确认或宿主一次性确认凭据；展示将删除的实际文件与关联产物。
4. 分件删除保留 provenance 并追加删除事件；先核对现有 `deleteBundle` 的代码、注释与审计策略是否一致，再明确整条删除和分件删除各自的留存规则。
5. 面板侧提供同样的入口（复用 `manual_capture_*` 的 RPC 风格）。

**验收**：四类各一条集成用例（删前存在、删后文件与行都消失、其他产物不受影响）；使用非规范但已登记的合法路径与越界路径各测一次；无人工确认凭据或无 `confirm` 均被拒；报告/PPT 关联文件不得残留。

### R6 AI / human 双模式与硬边界

**目标**：明确两种模式的边界，并把已经存在的强约束写成测试与文档。

**现状**：`lib/manual-capture.js:444` 对非 `agent` 发起的任务拒绝 Agent 浏览器动作（observe/click/viewer-download），但壳仍会响应真实下载事件并自动校验、归档。任务记录中的 `mode` 与 `requestedBy` 命名尚未完全对应，应以 `requestedBy` 等权威字段判定权限。

**改法**

1. 文档明确：
   - **AI 模式**：任务由 `lab_publisher_browser_download` 创建，Agent 按出版社 Skill 驱动页面；
   - **human 模式**：任务由面板/远端创建，Agent **只读状态**，不得 observe/click/导航/触发保存；壳可在用户真实点击后自动捕获、校验并直接归档。这里“无自动化”专指没有 Agent 页面操作，不禁止后台捕获与归档。
2. 补回归测试：非 agent 任务调用所有可改变浏览器页面、导航或下载状态的动作都必须被拒；调试工具仅暴露只读信息。
3. 将面板展示用的 `mode` 与权限字段 `requestedBy` 对齐；若暂不能迁移旧任务，文档明确优先级和兼容读取规则。

**验收**：全部写操作 × human 任务的拒绝用例；人工点击后的自动校验与归档照常完成；AI 任务不受影响。

### R7 人工点击轨迹记录（供规则学习）

**目标**：AI 能"读到人工点击过程"，作为总结出版社经验的输入。

**现状**：**不存在**。壳只记录 Agent 自己发起的 click；人在子 WebView2 里的点击无任何记录。

**改法**

1. 在既有常驻注入脚本 `WEBVPN_CHROME_SCRIPT` 中增加 capture 阶段监听（`pointerdown` + `click`），只在**任务处于 `armed/held` 期间**记录。
2. 每条记录只含**元素元数据**：`pageSeq`、时间戳、`tag`、可见文案（截断 80 字）、`href`（**脱敏：只留 host + path**）、`download` 属性、`target`、是否位于 iframe、元素在视口中的位置档位。

3. 壳内环形缓冲（最近 200 条），通过既有只读调试工具暴露：`lab_browser_debug` 增加 `humanActions[]`（与现有 `recentEvents` 同等级别的脱敏口径）。

**验收**：人工点一次下载入口后，`lab_browser_debug` 能给出该次点击的元数据，且**不含**任何查询串或表单值（安全用例必须显式断言）。

**风险**：即使是元数据，也可能带上敏感参数。→ 脱敏必须走与日志同一套 `redact_for_log`，并有专门的安全测试（参照 `tests/unit/webvpn-secrets-scan.test.mjs` 的思路）。

### R8 规则候选 → 确认对话框 → 人工复核后写入

**目标**（D2）：AI 归纳的新出版社经验**不能直接改规则文件**，必须经人工在对话框里确认。

**现状**：规则在 `skills/publisher-download/references/publishers.md`，标定表在 `docs/PUBLISHER_DOWNLOAD_CALIBRATION.json`。历史上出现过"未验证就当已支持"的账，本需求就是为了堵住它。

**改法**

1. **AI 只写候选**：新工具 `lab_publisher_rule_propose({ publisher, doi, kind, entryShape, observedBytes, sha256, note })` → 写入新存储表 `lab_capture_rule_candidates`，字段含 `status: "pending" | "accepted" | "rejected"`、`evidence`（DOI、日期、应用版本、字节、sha256、通路、访问方式）、`createdBy: "agent"`。验证范围精确到 DOI、文件类型、页面入口和 A/C 通路。
2. **客户端弹确认对话框**：面板列出 `pending` 候选（出版社、入口形态、证据、影响面、将写入的差异），提供 **接受 / 拒绝 / 稍后**。通过产品内工具/API 修改规则时，对话框和宿主记录的人工动作是必经入口；普通文件系统写入能力不在这项产品约束的控制范围内。
3. **写入由人工动作触发**：接受时由客户端调用宿主方法（如 `publisher_rule_apply(candidateId)`），宿主将规则合并到 `skills/publisher-download/references/publishers.md` 的对应条目。标定表只把**该入口/该通路/该文件类型**标为已验证，不因单篇成功就把整家出版社全部设为 `verified`；保留原状态及证据链。
4. **AI 侧的调用约束**：工具描述里写明"提交候选后必须告诉用户去面板确认，不得自行断言已支持"。

**验收**

- AI 调用后文件**未被修改**（断言 `publishers.md` 与标定文件字节不变）；
- 对话框接受后才改动，且改动内容与候选证据一致；
- 拒绝后候选变 `rejected`，不再出现在待办里；
- 现有 preset/技能导出校验（`preset-exports`）仍通过。

**风险**：对话框与宿主写入是新链路，需要既有的 client slot / host RPC 机制支持；实现前先确认 slot 注册契约（见 §11 第 6 项）。

### R9 单窗口同一时刻持有单任务；关窗即终止

**目标**：一个 WebView2 在同一时刻只持有一个活动任务；真正关闭该 WebView2 时，该任务必须终止，而不是继续被持有。多个排队任务可先后复用同一窗口。

**现状（这是个真实漏洞）**：`status()` 上报的 `pending_task_id` **不看 `window_open`**（`webvpn.rs:2433-2444`），插件侧的 `held` 也**不看 `windowOpen`**（`lib/capture-phase.js:122`）。用户关掉浏览器后，任务仍被判为"被该浏览器持有"，`phase` 停在旧值，AI 会一直等一个不会到来的变化。

**改法（Phase A）**

1. 壳侧把 WebView2 真正关闭、销毁或异常退出统一送入**幂等**的关闭转移：释放 `pending`，记录 `last_pending_task_id` 和 `release_reason`，状态给出 `pendingTaskId=null`、`windowOpen=false`。隐藏侧栏而 WebView2 仍存活时，不能触发此转移。
2. 插件侧将相应持久任务转为可审计的终态失败，`reasonCode=window-closed`；派生 phase 为 **`window-closed`**。`held` 必须要求 `desktop.windowOpen === true`，不能只在展示层隐藏待办。
3. 关闭转移完成后，迟到的下载事件、上传回调与旧令牌不得重新激活或登记该任务；用任务代次或等价校验防止旧回调落到重建任务上。
4. `nextAction=recreate-or-cancel`；`question` 明确“浏览器窗口已关闭，任务已终止；可重建”。已校验落盘的文件保留证据，临时文件按既有 TTL 清理。

**验收**

- 任务进行中真正关闭文献浏览器：状态工具在客户端下一拍内报 `window-closed`，`pendingTaskId=null`，持久任务为终态；
- 仅隐藏侧栏：WebView2 与任务继续有效；重复关窗回调不产生重复状态转移；
- 关窗后到达的下载/上传回调被拒，已归档文件不被误删；
- 重建任务可正常接管；
- 单测覆盖"壳报 windowOpen=false + pendingTaskId 非空"这一组合（当前正是缺这条）。

### R10 小球状态收敛（5 个正常态 + 3 个结果/异常态）

**目标**：小球对用户只表达**该不该动手**，内部状态机不因此简化。

**现状**：14 个 phase 直接映射 tone（`lib/capture-phase.js:58-75`）。

**改法**：新增一层**展示映射**（`ball.state`），内部 `phase` 保持完整：

| 展示态 | 文案（pdf / si） | 映射自 |
| --- | --- | --- |
| `loading` 页面加载中 | 正在打开出版社页面 | `queued` / `ready` / `navigating` / `waiting-download`(opening, searching) |
| `verification` 请点击验证页 | 请在侧栏完成人机验证 | `waiting-download` + `automationStage=verification` |
| `searching` AI 正在查找 | AI 正在查找正文 / AI 正在查找补充材料 | `waiting-download` + (manual/clicked) ∧ agent 模式 |
| `archiving` 归档中 | 正文归档中 / 补充材料归档中 | `downloading` / `saving` / `uploading` |
| `done` 任务完成 | 已归档到课题 | `completed` |
| `conflict` **已有文件** | 0.5.7：已有正文/SI，请保留或取消；0.5.8：可选择替换或删除 | R3 的建任务前独立冲突结果，或 `failed` ∧ `reasonCode=already-archived` |
| `failed` 归档失败 | 归档失败：<原因> | `failed` / `error` / `heartbeat-lost` / `orphaned` / `window-closed` / `stalled` / `expired` |
| `cancelled` | 已取消 | `cancelled` |

> 0.5.7 先交付 `conflict` 最小映射以满足 R3；0.5.8 再完成全表收敛。`failed`、`conflict`、`cancelled` 是三个不同的结果/异常态，优先级为 `conflict` 高于通用 `failed`。

**验收**：`PASSES` 全表用例（14 phase × 有/无 windowOpen → 期望展示态）；`phase` 字段的行为不变（回归）。

### R11 无固定等待：等待上限提升 + 页面加载完成即唤醒

**目标**：把"AI 反复短轮询"变成"一次长等待 + 事件唤醒"，压缩执行时间。

**现状**：`lab_browser_wait` 的指纹**已含页面维度**（`lib/tasks-tool.js:598`），任何 pageSeq/phase/字节变化都立即返回；瓶颈只是**上限 20 s**（工具超时 25 s）。客户端每 1.5–1.8 s 上报一拍。

**改法**

1. `lab_browser_wait` 上限 20 s → **120 s**（调用层超时需高于 120 s，拟为 130 s；先验证宿主/工具链允许该值）；等待期间心跳和取消均须继续生效。
2. 页面加载完成（`on_page_load Finished`，`webvpn.rs:4993-5030`）已经是 `pageSeq` 变化来源——确认它作为**第一类唤醒事件**，与阶段变化同级。
3. 可选效率项（同批或下一批）：把 `observe → click → wait` 三步并为一次调用（`lab_browser_click_and_wait`），减少 2 次模型往返。
4. 低思考强度执行：把"驱动捕获"委托给钉在快模型/低强度的子代理，主会话只收终态结论（属 preset/模型路由，不在本需求实现范围内，单独评估）。

**验收**

- 一次点击后，页面加载完成至 Agent 拿到新状态的 **p95 ≤3 s**；现有 1.5–1.8 s 客户端轮询不足以保证所有样本 ≤1.5 s。若必须进一步缩短，再设计推送唤醒；
- 120 s 等待期间取消、终态与超时都能正确返回，工具调用层不会先于业务超时中断；
- 端到端一次成功捕获的模型往返次数下降（改造前后各测 5 次取中位数，记录在发布说明里）。

### R12 多任务多窗口并行（分三阶段）

**目标**：探索并行捕获，缩短批量获取文献的总时长。

**现状的三个单例点**：窗口标签 `WINDOW_LABEL = "webvpn"`（约 20 处引用）、`pending: Option<PendingCapture>`、子 WebView2 是**嵌在主窗口侧栏里的一个矩形**（不是独立 OS 窗口）。好消息是**动作层已经是任务维度**：`WEBVPN_BROWSER_ACTION` 的 payload 带 `taskId`，上传端点、归档目录、任务状态都按 `taskId` 隔离。

**分阶段**

- **Phase A（0.5.7，必做）**：见 R9，修掉"关窗不终止"。
- **Phase B（0.6.0，评估后做）**：窗口标签按任务生成（`webvpn-<taskId>`）；`pending` 改 `Map<taskId, PendingCapture>`；侧栏加**任务切换器**（注意：这与 0.5.6 删掉的"页面内重复标签栏"不是一回事，那个是出版社页面里的假工具栏，这个是宿主侧的任务维度）；`client/src/webvpn-tab.js` 目前只有一个浏览器页签实例，要按 `taskId` 维度管理；并发上限 **2–3**（每个 WebView2 约 100–200 MB）。

**已知难点**：焦点/前台管理本就脆弱（β28/β29 都在修），多窗口会放大——必须显式设计"激活哪个窗口"，否则会互相抢焦点。

**验收（Phase A）**：见 R9。**Phase B/C 只出评估结论与原型数据，不在本批承诺交付。**

### R14 捕获上限统一提高到 250 MiB

**目标**：正文和 SI 的最大完整文件由 100 MiB 提至 **250 MiB（262,144,000 字节）**。这是二进制 MiB 上限，界面可显示“250 MB”，文档和接口以字节数为准。

**改法**

1. 统一检查并修改壳内 `CAPTURE_MAX_BYTES`、CDP Fetch 解码前后检查、下载事件/SI 捕获、状态里的 `maxCaptureBytes`、上传请求的 `Content-Length` 与实际流量限制、`src/manual-capture.js`、`lib/literature-browser.js` 的 PDF 文件级校验及 OA 链路默认 `maxPdfBytes`；同步 `desktop/src-tauri/resources/bridge/capture-spec.json` 与 `browser-extension/ibm-literature-capture/capture-spec.json` 两份镜像，以及桥宿主默认值和相关手册。两份 spec 的 `maxFileBytes` 必须逐字节一致，不要只修改提示文案。
2. 所有路径都在声明长度和实际接收字节两个位置实施上限；缺少 `Content-Length` 时仍必须在读取中止于上限，超限返回 HTTP 413 / `reasonCode=too-large`。不得把被截断的 PDF 或 HTML 挑战页登记为成功。
3. 实施前核对 Node、WebView2 与 CDP Fetch 的峰值内存：base64、解码 buffer、上传 buffer 可能同时存在，250 MiB 文件的瞬时内存显著高于 250 MiB。若现有一次性缓冲无法稳定处理，先改为有界分块/临时文件流转，再启用新上限；不得仅提高常量后发布。

**验收**：99 MiB、100 MiB、介于 100–250 MiB、恰好 250 MiB 的有效 PDF 均可完成校验与归档；超过 250 MiB 一个字节、虚假或缺失长度、解码膨胀、下载中途超限均明确拒绝，原文件及任务登记不被污染；记录 Windows 真机峰值内存与耗时。测试可用合成 PDF/流，不要求下载实际大论文。

## 5. 状态机规范（更新版）

### 5.1 壳内会话（增加真关窗转移）

```
Closed → Opening → WaitingLogin → Ready → Navigating → WaitingDownload
                                              ↓             ↓
                                        Downloading → Uploading → Ready
   Expired → Ready        Error → Opening|Closed        任意态 → Closed|Error
```

### 5.2 任务持久态

```
armed → uploading → completed
  │         │
  ├─────────┴→ failed（带 reasonCode）
  ├→ expired      └→ cancelled
```

新增或明确字段：`reasonCode`（R4，0.5.7）、`accessMode ∈ {iwan, oa, webvpn, direct}`（R1，0.5.8，必须持久化实际归档通道）。0.5.7 **不新增可由 Agent 设置的 `allowOverwrite` 授权布尔值**；0.5.8 替换使用宿主记录的一次性人工确认凭据。

### 5.3 派生 phase（+1）

在现有 14 个之外新增 **`window-closed`**（终态，R9）。`deriveCaptureView` 的"唯一真相"定位不变：工具、小球、面板提示条继续共用。

### 5.4 决策机（nextAction，不变）

`observe-or-click` / `wait-and-poll` / `download-viewer-pdf` / `retry-download-entry` / `manual-handoff` / `complete-verification` / `recreate-or-cancel` / `done`。
新增映射：`already-archived` → 0.5.7 预检返回独立冲突结果，已有任务的 409 才使用 `recreate-or-cancel`；选项先为“保留/取消”，0.5.8 再开放经人工确认的替换/分件删除。`window-closed` → `recreate-or-cancel`。

### 5.5 目标流程（与你的设想对齐后）

```
发起 DOI 任务
  └─ 通道判定（插件+壳决定，AI 只读 accessMode）
       ├─ iWAN 可用 → 直连（OA/非 OA 一致）
       ├─ oaProbe 社 → 探 OA → 命中=oa / 未命中=webvpn
       └─ 闭源社 → webvpn（未登录则请用户登录）
  └─ 页面加载完成（事件唤醒）→ AI 判断
       ├─ 验证页 → 请用户点击（AI 只等，无自动化）
       ├─ 文章主页 → 按出版社 Skill observe/click
       └─ 原生 PDF 文档 → C（CDP Fetch）自动取正文
  └─ 建任务前或归档时检查冲突 → 有冲突显示「已有文件」并停止；无冲突才归档完成
```

## 7. 非目标（本方案不做）

1. **不做**通用下载器：仍只处理已登记 DOI 的出版社页面。
2. **不做**验证码自动破解：人机验证永远由人完成（这是红线，不因本方案改变）。
3. **不导出**任何 Cookie / 票据 / 完整签名 URL；不读 WebView2 profile。
4. **不做** Node 侧抓取出版社正文页（只有 OA 分支允许 Node 侧无凭据抓取 PDF）。
5. **不承诺**多窗口并行在本批交付（R12 只承诺 Phase A）。
6. **不承诺**八家出版社标定完成（R13 只改有实测证据的项）。

## 8. 风险登记

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| R2 删 206 装配后，某站点只有 Range 响应 | C 无法取得完整正文 | Range 请求已在代码中观察到；A 真实下载入口或人工保存为兜底，二者均不可用时明确失败并记录 DOI，不登记片段 |
| R1 OA 探测被外部服务拖慢 | 任务变慢 | 只对 `oaProbe` 社、元数据优先、硬超时、结果缓存、失败不阻断 |
| R3 冲突预检与端点校验不一致 | 仍可能覆盖 | 端点为最终权威；同一条目/文件类型串行化检查与登记，禁止先删旧文件再重命名 |
| R5 分件删除误删 | 数据丢失 | 实际登记路径核验、人工确认凭据、越界检查、删除前展示清单；`confirm=true` 不能代替人工同意 |
| R14 提高上限导致内存峰值过高 | 壳或 Node 进程崩溃 | 发布前实测 250 MiB 峰值；必要时采用有界流式处理，而非仅改常量 |
| R7 轨迹记录泄露敏感参数 | 安全 | 仅元数据、`redact_for_log` 同口径、专门安全测试、可关闭 |
| R8 对话框改文件 | 规则被误改 | 人工确认是唯一入口、写前展示 diff、可回滚（保留改动前副本） |
| R12 多窗口抢焦点 | 体验退化 | Phase B 前先做焦点方案评审，必要时限制并发为 1 + 隐藏窗口并行 |

## 11. 实施默认决策与仍需验证的技术条件

以下是本稿采用的实施默认值，无须就同一事项再次请求用户确认：

1. R1 初始 `oaProbe` 仅 Nature、Springer；arXiv 无 DOI 场景不并入本次出版社捕获，另案评估。
2. R3 人工替换保留一份带 sha 的旧文件备份；备份不作为当前正文参与检索或展示，恢复动作单独提供。
3. R2 的 D 仅供人工兜底，不作为自动获取路径；保留与否以人工回归和无调用证据决定。
4. R5 删除报告/PPT 时，以其实际登记的关联产物为一组展示并处理；证据截图、文内引用先核对引用关系，不作未展示的级联删除。
5. R6 human 模式维持现状：人工触发下载后自动校验并直接登记，不新增“待确认”中间态。
6. R8 坚持真实对话框与宿主记录的人工动作；实施前先验证 slot/RPC 契约。若不可行，保留候选、不写正式规则，另提设计变更；`confirmedByUser=true` 不能替代对话框。
7. R11 暂定 120 s 长等待；实施前验证工具链超时和取消能力，未通过则维持 20 s 并单列阻塞原因。
8. R12 Phase B 原型并发上限从 **2** 起，先评估隐藏窗口并行；真实可见多窗口需另做焦点评审。

**发布前必须取得的证据**：0.5.7 的 A/C 壳内回归日志及文件校验、Range-only 页面的明确兜底结果、250 MiB 压力测试数据、冲突与关窗状态的全链路测试。标定文件只填写能够对应 DOI、版本、字节与 sha256 的记录。
