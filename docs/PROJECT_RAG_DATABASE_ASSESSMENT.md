# 课题内论文 RAG 数据库：可行性评估与工作量

> 问题：能不能把**课题里已经归档的论文**做成检索增强（RAG）知识库，让科研 Agent
> 回答问题、写综述时先检索本课题的全文，而不是只读当前上下文？
> 本文件给出：现状盘点、四种技术路线、逐项工作量、风险与建议分期。

## 1. 现在手上已经有什么

| 资产 | 位置 | 对 RAG 的价值 |
|---|---|---|
| 归档正文/SI | `<课题工作区>/literature/<entryStem>/<entryStem>.pdf`、`<…> SI.pdf` | 语料本体；命名规范可直接做文档标识 |
| 精读报告 | 同目录 `<stem> 精读报告.md/.docx` | **已由模型消化的高质量摘要**，是「低成本切片」 |
| 综述报告 | `<workspace>/literature/reviews/<runStem>/<runStem> 综述报告.md` | 跨文献的现成综合 |
| 登记表 | storage-domain（JSON 后端）：`paper_source_bundles` / `reading_reports` / `literature_search_runs` | 元数据、DOI、哈希、状态；可做过滤与增量判断 |
| 内容哈希 | `pdfSha256` / `artifactSha256` / `siSha256` | **增量索引的天然 key**（文件没变就不重嵌） |
| 文档转换 | `scripts/markitdown/convert.py`（PDF/Office → Markdown）、`labConvert` 服务 | 现成的抽取层，RAG 的解析步骤不必重写 |
| 预览链路 | `/api/lab-artifacts?kind=pdf|report|ppt` | 回答时给可点击的原文定位 |
| provenance | `artifact_provenance`（输入哈希/skill 版本/模型/时间） | 索引版本可审计 |

**缺的两块（关键）**：

1. **没有向量库**：全仓库无 embedding/vector/cosine 相关代码；storage-domain 是 JSON
   文档后端，不是向量索引。
2. **没有 embedding 接口**：DSH 的模型面只有 `llm`（`llm/stream`），**不提供
   embeddings 端点**（已在 `@deepseek-ai/dsh-llm` 的导出里核对）。也就是说要做向量检索，
   必须自己接一个 embedding 提供方（远程 API 或本地模型）。

## 2. 四条技术路线

| 路线 | 检索方式 | 需要新增 | 优点 | 代价 |
|---|---|---|---|---|
| **A. 关键词/FTS** | Markdown 切块 + SQLite FTS5（或 node:sqlite 全文索引） | 切片器 + FTS 表 + 检索工具 | 零外部依赖、离线、可进安装包；中文需分词或 trigram | 语义召回弱（同义改写查不到） |
| **B. 远程 embedding** | 切块 + 远程 embedding + 向量表（sqlite-vec/自写 cosine） | embedding 客户端 + 向量存储 + key 管理 | 效果好、实现快 | 依赖外网与密钥；**把论文全文发给第三方**（多数是订阅版权内容，需用户显式同意） |
| **C. 本地 embedding** | 同上，模型本地跑 | ONNX 运行时 + 模型权重（多语言 ~100–500MB） | 离线、隐私好、与「本机受控运行边界」一致 | **安装包体积再涨**（当前已 259MB）；CPU 推理慢；Windows 打包需带 ONNX DLL |
| **D. 混合（推荐）** | FTS 先召回 → 可选重排（远程或本地） | A + 可选 B/C | 先可用再增强；不把体积/密钥风险绑死在第一步 | 需要一次重排开关与降级路径 |

## 4. 风险与前置决策

1. **体积**：本地模型路线会把安装包再推高 100–500MB。当前 0.1.7 适配后安装包已从
   172MB 涨到 259MB（上游 `libreoffice-kit-win32-x64` 325MB 解压体积），本地模型
   需要单独评估是否需要「按需下载 + 校验」而不是随包。
2. **版权与合规**：出版社 PDF 通常是订阅内容。**绝不能**把全文默认发给第三方
   embedding 服务；必须逐次同意、说明发送范围，并优先本地路线或只索引开放式内容。
3. **模型面缺口**：DSH 只有 chat 流式接口，没有 embeddings；B 路线要自带客户端与
   密钥配置入口（现无「embedding 配置」设置项）。
4. **中文检索**：FTS5 默认分词对中文无效，需要 `tokenize='trigram'` 或额外分词；
   否则中文查询召回很差（这是 A 路线最容易踩的坑）。
5. **索引一致性**：`deleteBundle`/改名（`setEntryNaming(mode:apply)`）都会移动或删除
   文件，索引必须有对应的失效钩子，否则会出现「检索命中已删条目」。
6. **评测缺失**：现在没有检索评测集。建议先用 20–30 个真实问题建一个小评测集，
   否则「效果好不好」无法判断，容易陷入无限调参。

## 5. 建议路线

1. **阶段 0（1–2 人日，先验证价值）**：不改存储，写一个只读脚本：把一个课题的
   `literature/**/*.md`（先用 markitdown 转一遍）做朴素关键词检索，用 10 个真实问题
   手工看召回。**先确认「课题内检索」确实有人用**，再投入。
2. **阶段 1（7–9 人日）**：A 路线最小可用（SQLite FTS5 + 中文 trigram + 两个工具），
   只索引精读报告与正文 Markdown，UI 只给一个「知识库」状态页。
3. **阶段 2（+6–8 人日）**：按需加混合重排（远程 embedding，逐次同意）或本地小模型，
   并补引用定位与评测集。
4. **阶段 3**：与综述流程打通——`lab_tasks_get_review_inputs` 增加「本课题历史相关片段」
   作为综述输入，这是 RAG 在本项目里最自然的落点。

**结论**：技术上可行，且已有资产（归档目录、哈希、markitdown、storage-domain）能省掉
约三分之一工作量；主要不确定性不是算法而是**体积、版权、以及中文检索**三件事。
建议按「阶段 0 → 阶段 1」推进，总投入 **8–11 人日**可得到可用的课题内检索，
完整混合方案约 **23–29 人日**。
