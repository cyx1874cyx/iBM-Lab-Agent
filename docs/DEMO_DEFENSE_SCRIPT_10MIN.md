# iBM Lab Agent：6 分钟演示与 4 分钟答辩讲述稿

> 适用对象：校内评委老师、阿里工程师  
> 当前演示版本：v0.5.0  
> 推荐形式：2 张讲解页 + 软件实机演示  
> 核心句：**模型负责推理，宿主负责可信执行，研究人员保留最终决定权。**

## 一、演示前准备

### 1. 推荐的屏幕顺序

1. 标题页：软件名称、一句话定位、团队信息。
2. 总体架构图：打开 `ibm-agent-architecture.html`，预先缩放到能看清五层结构。
3. iBM Lab Agent 软件：预先打开一个内容完整的示例课题。
4. 结束页：三点价值与一句结束语。

### 2. 软件中应预先准备的内容

- 一个名称易懂的示例课题，例如“聚前药载体文献与合成研究”；
- 一份简洁的课题核心记忆，至少包含研究目标、约束和当前进展；
- 一条已经完成的文献检索记录；
- 一篇已经归档 PDF/SI 的文献；
- 一份处于“待审核”或“已批准”状态的精读报告；
- 一份可正常打开预览的文献汇报 PPT；
- 一条具有原文证据和版本记录的合成路线；
- 一条已经进入审核流程的 NMR 或表征任务。

### 3. 现场演示原则

- 不现场等待完整的文献检索、长文精读或 PPT 生成；这些操作受网络和模型速度影响。
- 现场主要展示已经完成的结果，以及打开、追溯、审核、退回等确定性动作。
- 可以新建一个对话展示任务如何发起，但不必等待任务跑完。
- 软件、架构图和结束页都提前打开；关闭无关窗口和系统通知。
- 计时到 5 分 20 秒时，无论演示到了哪里，都切入总结。

## 二、6 分钟主讲逐字稿

### 0:00—0:35｜开场：我们解决什么问题

【画面：标题页】

各位老师、各位工程师，大家好。今天我演示的是 **iBM Lab Agent**，一个面向科研课题组的本地科研工作台。

科研工作的问题通常不是“缺少一个会聊天的模型”，而是文献、实验方案、结构式、原始数据和汇报文件分散在不同软件里。普通 AI 对话可以给出答案，但很难持续记住一个课题，更难回答三个关键问题：**结论依据是什么、文件经历了哪些修改、最终由谁批准。**

所以我们想做的不是一个科研聊天机器人，而是一套把 AI 推理、科研工具、课题数据和人工审核组织在一起的工作系统。

### 0:35—1:15｜产品定位与核心原则

【画面：切到总体架构图】

iBM Lab Agent 当前以 DeepSeek Harness 插件形式运行，不修改 Harness 核心，同时提供 Web 和 Windows 桌面端。

这张图中，上层是研究人员看到的课题工作台；中间是文献、合成、化学、NMR、表征和模板等科研服务；下层连接本地工作区、版本记录，以及 Origin、MestReNova、Python 等科研工具。

整个系统最重要的原则可以概括为一句话：**模型负责推理，宿主负责可信执行，研究人员保留最终决定权。** 模型可以阅读、规划和生成内容，但文件写入、版本保存、哈希校验、工具调用和审批状态由确定性程序管理。

### 1:15—1:55｜进入软件：以课题为中心，而不是以聊天为中心

【动作：切到软件首页，进入预先准备的示例课题】

这里不是一个空白聊天框，而是“我的科研课题”。每个课题对应一个独立工作区，文献、任务、报告、实验方案和表征结果都归档在这个课题下，避免不同项目互相污染。

【动作：点击“核心记忆”】

这是课题的长期核心记忆。它记录研究目标、材料体系、已有结论和约束条件。每次修改都会提交为新版本，旧版本仍然可追溯。这样，科研 Agent 不需要依赖越来越长的历史对话，也不会因为换了一个会话就失去课题背景。

### 1:55—3:20｜核心演示：文献从检索到可信交付

【动作：进入“文献资料”】

下面演示一条最典型的科研链路：从文献到可审核交付。

左侧是按会话归档的检索记录。系统可以整合多来源结果、去重、核验 DOI，并保存 RIS。右侧是文献精读档案，每篇文献可以关联正文 PDF、Supporting Information、精读报告和汇报 PPT。

【动作：打开一篇已经归档的文献或文献概览】

如果开放来源没有全文，软件不会声称已经读过原文，也不会绕过学校或数据库授权。它会明确标记缺失状态；研究人员可以通过自己已经授权的浏览器会话补充 PDF 或 SI，再归档到本课题。

【动作：打开精读报告预览】

报告不是生成后直接下载。系统先把实际 DOCX 渲染成分页预览，并给出自动自查提醒。研究人员可以逐页检查，然后选择“审核通过”或者“退回修改”。自动检查只提供提示，不能代替人的科学判断。

【动作：指向审核状态、下载按钮或哈希信息】

审批绑定的是当前文件的 SHA-256。如果文件被重新生成或修改，旧批准不会自动沿用，必须重新审核。系统还保存 provenance，也就是这份产物使用了什么来源、模板、模型和技能版本。这样，交付的不只是一个文件，还有它的证据链。

### 3:20—4:20｜从文献延伸到合成与化学工作流

【动作：进入“研究设计”，打开一条预先准备的合成路线】

iBM Lab Agent 不只管理文献。以合成路线为例，它可以记录靶标、逐步反应条件、结构式、证据来源和可行性检查。

路线中的信息会区分“文献提取”“人工修改”“Agent 优化”和“模型推断”。这一区分很重要，因为模型提出的候选条件不能伪装成已有文献事实。

路线可以多次修订，但最终锁定必须由可信的用户界面动作完成。系统不会自动采购，也不会自动执行实验；它负责把证据、建议、版本和审批组织清楚，让研究人员做最后决策。

### 4:20—5:05｜NMR、表征和本地科研软件协同

【动作：进入“表征分析”，展示一条 NMR 记录】

在 NMR 和表征模块中，系统登记原始 FID、结构文件、峰积分和组成计算，并通过明确的状态机推进：准备、待审核、批准写回、视觉确认。

原始数据不可被覆盖；审核失败会回到可修订状态，而不是偷偷替换已经批准的结果。需要时，软件可以通过本地 MCP 桥接 Origin 和 MestReNova。工具不可用时会明确降级并报告原因，不会伪造已经完成的科研结果。

### 5:05—5:35｜工程可信度与安全边界

【画面：可切回架构图，或停留在软件审核状态】

从工程角度，系统采用本地优先设计：课题文件默认保留在用户机器；桌面服务只监听 `127.0.0.1`；密钥使用 Windows 用户级加密保存；外部网页不能直接获得桌面 IPC 权限。

项目同时覆盖 Node、浏览器、Python Bridge、Rust/Tauri、回归和安装包验证。对我们来说，科研 Agent 的价值不只是“回答得像不像”，还包括失败是否显式、产物是否可追溯、权限是否越界。

### 5:35—6:00｜总结

【画面：结束页】

最后总结三点。

第一，iBM Lab Agent 把一次性 AI 对话变成了持续的课题工作区。  
第二，它把文献、合成、表征和科研软件连接成可追溯的工作流。  
第三，它没有把科学责任交给模型，而是通过版本、证据、哈希和人工审核建立可信边界。

我们希望它最终成为科研人员的本地智能工作台：**让 AI 提高效率，但让证据、数据和决定始终掌握在研究人员手中。**谢谢各位。

## 四、4 分钟答辩高频问题

### 问题 1：它和 ChatGPT、通义千问或普通 Agent 平台有什么区别？

**建议先答：区别不在于再做一个模型，而在于把模型放进可治理的科研工作流。**

通用聊天产品通常以会话为中心；iBM Lab Agent 以课题为中心，具有独立工作区、版本化核心记忆、任务状态、科研产物索引和人工审核。模型生成的报告、路线和表征结果不是聊天附件，而是带来源、哈希、版本和审批状态的课题资产。模型可以替换，课题数据和可信执行层仍然保留。

### 问题 2：怎么解决大模型幻觉，能保证科研结论正确吗？

**建议先答：不能承诺模型永不出错，所以系统设计目标不是“消灭幻觉”，而是让错误可识别、可追溯、可阻断。**

系统区分文献事实、人工修改、Agent 优化和模型推断；全文缺失时明确标记，不能假装完成精读；产物保存来源链并经过人工审核；重要文件的批准绑定具体哈希。也就是说，模型负责提出和解释，证据与人工门禁负责决定能否进入正式交付。

### 问题 3：科研数据和 API Key 是否会泄露？

**建议先答：系统采用本地优先和最小权限设计。**

课题数据默认放在用户自己的本地工作区，桌面服务只监听本机回环地址。Windows 端的 API Key 使用当前用户的 DPAPI 加密。外部文献网页与主应用 WebView 权限隔离，浏览器捕获只接收用户已经获得授权的文件。对于发送给模型的内容，仍需按照所选模型服务的数据策略管理，因此敏感课题可以进一步接入校内或私有模型。

### 问题 4：为什么选择插件架构，而不是从头开发完整平台？

**建议先答：我们把通用 Agent 基础设施与科研领域能力分开。**

Harness 提供会话、模型和工具基础能力；iBM Lab Agent 只叠加课题管理、科研服务、技能和可信门禁，不修改宿主核心。这样减少重复开发，也让模型和通用基础设施可以升级。代价是必须严格管理版本兼容，因此项目使用固定依赖、锁文件、诊断脚本和发布验证来控制风险。

### 问题 5：系统如何扩展到更多学科或更多工具？

**建议先答：扩展点分为技能、领域服务和工具适配器三层。**

新的内容方法可以作为 Skill 接入；需要持久状态和业务规则的能力作为领域服务接入；Origin、Mnova 或其他软件通过 MCP、Python 或受控子进程适配。三层分开后，新学科可以复用课题、版本、产物和审核基础设施，只替换领域技能与工具适配器。

### 问题 6：你们如何证明它真的提高了科研效率？

**建议先答：当前已经证明了流程闭环，下一阶段要用真实课题做量化评估。**

建议选取文献精读、组会 PPT 和 NMR 归档三个高频任务，比较使用前后的完成时间、人工修改轮次、引用错误率、遗漏率和可追溯完整度。我们不只统计“生成速度”，还统计审核成本和返工成本，因为科研场景里快但不可核验并不等于高效。

### 问题 7：如果 Origin、Mnova、网络或模型服务不可用，会怎样？

**建议先答：系统采用显式失败和可恢复降级，不把失败包装成成功。**

外部工具调用有预检、状态和错误记录；不可用时保留原始数据与任务状态，允许人工处理或稍后重试。已经生成和审核的本地产物仍可访问。发布前也通过诊断和目标机器验收清单确认本地软件与授权环境。

### 问题 8：目前最大的不足是什么？

**建议先答：当前最大的挑战是工程规模化，而不是再增加更多按钮。**

一是不同发行清单的版本信息仍需进一步统一；二是远程接口和领域服务数量增加后需要继续模块化；三是机构文献访问和商业科研软件无法完全在 CI 中复现，需要真实环境验收；四是科研效果还需要更多课题和用户数据进行量化评估。我们已经把这些列为发布一致性、可观察性和真实用户评估的下一阶段重点。

### 问题 9：为什么一定要人工审核，会不会降低自动化价值？

**建议先答：人工审核不是自动化失败，而是高风险科研流程中的责任边界。**

系统自动完成检索整理、格式转换、自查、版本登记和重复劳动，把人的时间集中在科学判断上。对于普通草稿可以高自动化；对于正式报告、合成路线和表征结论，则保留人工门禁。自动化程度应与风险等级匹配。

### 问题 10：如果模型更换，已有课题和产物还能使用吗？

**建议先答：可以，系统刻意把模型与课题资产解耦。**

课题记忆、任务、文件、版本、哈希和来源链由宿主服务保存，不依赖某一次模型会话。更换模型后，新任务仍可读取同一个课题上下文；历史产物还会记录当时使用的模型和技能版本，便于比较和复现。

## 五、出现故障时的备用讲法

### 软件启动失败

“现场环境没有完成本地服务启动，我改用已经生成的交互架构图和结果截图说明。桌面端本身设置了健康检查和显式失败机制，这个故障不会被伪装成系统已经正常运行。”

### 模型响应过慢

“完整精读是异步长任务，演示现场不等待生成。我现在展示同一流程已经登记的结果、来源和审核状态，这也是实际使用时更重要的交付环节。”

### 文献网页或网络不可用

“软件不会在未获得原文时假装完成精读。这里可以看到已归档的离线 PDF、SI 和报告；网络恢复后，任务可以从当前状态继续。”

### Office、Origin 或 Mnova 无法打开

“外部科研软件属于可诊断适配器。当前失败不会修改原始文件，也不会把任务标成成功；我们可以查看已经保存的预览、状态与 provenance。”

## 六、最后一分钟删减策略

如果现场只剩 1 分钟，按以下顺序保留：

1. 一句话定位：不是聊天机器人，是本地科研工作台。
2. 打开一个课题并展示版本化核心记忆。
3. 打开文献报告预览，指出人工审核、SHA-256 和 provenance。
4. 用一句话带过合成和 NMR。
5. 用“模型推理、宿主执行、人工决定”收尾。

## 七、表达注意事项

- 不说“完全消除幻觉”，改说“让错误可识别、可追溯、可阻断”。
- 不说“全自动科研”，改说“自动处理重复工作，关键科研决定由人审核”。
- 不说“支持所有学科”，改说“当前首先覆盖聚前药与高分子材料研究，架构可扩展”。
- 不说“能够自动下载任何论文”，改说“在开放获取或用户已授权的范围内归档全文”。
- 不把测试通过等同于科学结论正确；工程验证和科研有效性评估应分开表述。
- 面向老师，多讲科研痛点、证据和责任边界；面向工程师，多讲模块边界、状态机、失败语义和可扩展性。
