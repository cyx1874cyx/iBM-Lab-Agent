# v0.5.5-beta26 发布说明

发布日期：2026-09-29

## 主题：点查看器**自己的保存控件**——就是那个够不到的工具栏按钮

β24 的"在 WebView2 网络会话里重新读取 PDF URL"（CDP `Network.loadNetworkResource`）在现场失败了，
而原因现在看得见：这些出版社给的是**一次性签名 URL**，让网络栈第二次请求同一个地址，拿到的不是同一份资源。
这条路不再调参，直接去掉。

### 现在怎么做

用户要的本来就是"点预览页工具栏里的保存"。那个按钮在 **Chromium PDF 扩展的一串 Shadow DOM 里**
（`#viewer → #toolbar → #downloads → #save`），页面脚本进不去，但 **CDP 可以**：

- 用 `Page.getFrameTree` 拿到各 frame 的 id；
- 在 **PDF 扩展自己的执行上下文**里求值一段脚本：先试主上下文，再逐个试子 frame 上下文；
- 脚本找到并**点击 `#save`**（回退 `#download` / `#save`，并检查 disabled/hidden），
  返回 `clicked` 或确切原因（`viewer-unavailable` / `toolbar-unavailable` / `save-unavailable`）。

点的是查看器自己的保存 → **变成一次普通的浏览器下载** → 文件、进度、归档全部走**从一开始就可靠的那条下载通路**。
**不构造第二条 HTTP 请求，也不把签名 URL 交给页面脚本。**

失败时 `clear_viewer_save_action` 只撤销动作标记（不动 `download_claimed`），
**人工 Ctrl+S 仍会被下载事件认领**；操作错误保留完整细节（1024 字符上限）。

### AI 侧同步

工具描述改为"触发查看器保存控件"；去掉 `webview-network` 进度来源；
Skill 明确：**保存控件不可用、或 12 秒内没有下载事件 → 一次即转人工**，不反复去要一份签名 PDF。

## 真机验收

1. **原生 PDF**：进 PDF → 调保存（或点右下角浮层）→ 日志应出现
   `directPdfFetch … 已点击查看器保存控件`（或操作结果里给出 `viewer-unavailable` / `save-unavailable`），
   随后是 `downloadRequested`（目标为任务暂存路径）→ `captureCompleted`。
2. **失败可诊断**：如果给出的原因是 `save-unavailable`，说明这台机器上的 Chromium PDF 查看器
   DOM 结构与脚本预期不同——请把该行原文发我，我按实际的 shadow 结构再对一次。
3. **人工兜底**：在侧栏 PDF 上按 Ctrl+S，仍应被捕获归档。
