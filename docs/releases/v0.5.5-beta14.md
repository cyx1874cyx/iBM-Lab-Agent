# v0.5.5-beta14 发布说明

发布日期：2026-09-27

## 主题：载荷完整性——不许把半个 PDF 送去归档

beta13 现场（`issue-0.5.5-beta13.md`）复现了一条**新失败模式**，报告把它定位到了行：

```
click  Download PDF • 2.6 MB  →  进入预览器
wait                           →  saveReady=true, downloadedBytes=13361（还在涨）
save_current_pdf               →  ❌ HTTP 400；留下 capture-…-pdf-未归档.pdf = 262144 B
```

那 262144 字节是**恰好 256 KiB**、有 `%PDF-` 头、**没有 `%%EOF`** 的半截文件。
真实大小 2,716,668 B。三处缺陷叠在一起才造成它：

| # | 位置 | 缺陷 |
|---|---|---|
| 1 | 壳 `write_stream_to_file` | 把 `IStream::Read` 返回 0 当成 EOF。这个流由网络响应驱动，**暂时没数据时也会返回 0**；于是在一个缓冲边界上提前收工，只拿到 256 KiB |
| 2 | 壳 `finish_pdf_payload` | `complete = bytes > 0`——**有字节就算完整**，截断载荷被标成"已就绪" |
| 3 | 插件 `capture-phase.js` | 归档门只看 `pdf.ready`，不看 `complete`；消息又把分片大小当总长报（「已就绪（256.0 KB）」） |

结果：调用方**被信号引导**去归档一个还没下完的文件，归档服务按规矩拒收（400），
而真正的原因（载荷没下完）已经在链条里丢失。

### 1. 壳（D1/D2/D3）

- **读流不再把空读当 EOF**：持续读，直到**正向证明**完整——收满 `Content-Length`，
  或尾部出现 `%%EOF`；都没有就在「5 秒无新数据 / 180 秒总上限」后停下并**如实报未收全**。
- **`complete` 只来自正向证明**；`ready` 的语义边界写进代码注释：
  `ready` = 至少进来了一个字节，`complete` = 已证明收全（此前两者的表达式是同一个，
  于是"正在接收"这个状态对外根本不存在）。
- **归档前三道校验**：`%PDF-` 头 ∧ 尾部 `%%EOF` ∧ 大小等于 `Content-Length`。
  任何一条不过就直接返回「载荷不完整（已接收 X / 共 Y），未归档」，
  **绝不再把半截文件交给归档服务换一个 400**。
- **进度两条路一起算**（R2）：`downloadedBytes` 取「下载目标文件」与「响应层载荷」的较大者。
  此前只看下载目标，走响应层时状态里**始终没有进度数字**——用户要的"速度和总大小"
  就是这么丢的。

### 2. 插件（D5/D6/D7）

- **归档门加 `complete`**：`save-pdf-ready` 只可能出现在载荷被证明收全之后（D5）。
- **新分支：正在接收**。消息形如
  `PDF 正在接收（1.0 MB / 2.6 MB，39%，约剩 3 秒）；收满后 nextAction 会变成 save-pdf-ready，现在不要归档`，
  且 `nextAction=wait-and-poll`。**总量未知时省略百分比**，只说「总大小未知」——
  报一个假的百分比比不报更糟。
- **新分支：载荷未收全**：`nextAction=retry-download-entry` + `alternateEntry`，
  消息带「已接收 X / 共 Y」与壳给的原因（D2/D5 的用户可见面）。
- **`progress` 对象**（D6）：`{receivedBytes, totalBytes, percent, speedBps, etaSeconds}`，
  速度由相邻两次 `(时间, 字节)` 采样得出，样本不足时**省略**而不是给 0。
- **指纹补载荷维度**（D7）：`pdf.complete` / `pdf.contentLength` / `progress.receivedBytes`
  进 `lab_browser_wait` 的指纹——少了它们，"收完"那一刻若不改变 phase/status 就不会唤醒 wait。
- 停滞判据明确为「无字节增长 ∧ 无新采样时间」，并且长耗时判据纳入"响应层正在收载荷"
  （否则 state 仍是 `waiting-download` 时进度与停滞双双失效）。

### 3. 预设（D9）

判据改成 `nextAction`（不再教模型看 `saveReady` 布尔值）；新增两条：`phase=downloading`
或消息里出现「正在接收」时**只等不归档**；任何恰好是 2 的整次幂的字节数
（262144、524288、1048576…）先按"截断"处理。

## 本版**未**做，以及原因

- **页内浮层「保存到课题」按钮**（报告的方案 A）：原生 PDF 查看器不属于页面 DOM，
  注入脚本在那里**不执行**，浮层在 R1 的主要场景（裸查看器）里根本不会出现。
  资源层落地（方案 B）才是那条路，本版把它修对了（beta13 已经实现但完整性判据是错的）。
- **动作延迟**（客户端 1.8 秒轮询节拍）仍排队；`browser_operation_claim` 长轮询下一轮做。
- 八家出版社的 iWAN 标定仍全为 `pending`——需要人工在真机逐家验收，**本轮不声称完成**。

## 真机验收（按顺序）

1. **半截载荷不再被归档**：复现报告 §8 第 4 步——在 `downloadedBytes` 还在涨时调
   `lab_browser_save_current_pdf`，必须得到**明确拒绝**（载荷不完整 / 未收全），
   而不是一个 HTTP 400；也不得产生 `-未归档.pdf` 之外的错误产物。
2. **进度可信**：`phase=downloading` 期间每次读状态都能看到
   `progress.{receivedBytes,totalBytes,percent,speedBps,etaSeconds}`（总量未知时无 percent）。
3. **完成即事件**：载荷收满那一刻 `lab_browser_wait` 立即返回 `save-pdf-ready`，
   随后保存返回 `{path,bytes}`，字节数与页面上标称的大小一致（Science ePDF 应为 2.6 MB 级）。
4. **裸查看器仍可归档**：点 `Download PDF` 进原生 PDF → 等到 `save-pdf-ready` → 保存成功
   （这一条是 beta13 没做到的）。
