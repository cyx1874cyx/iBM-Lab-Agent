# v0.5.5-beta13 发布说明

发布日期：2026-09-27

## 主题：闭环收口——一份真相、终态可执行、入口可判别

beta12 把浏览器交给了 AI，但只交了一半：状态机暴露的是「壳内脚本自动跑」的语义，
AI 看得到阶段快照，看不到页面事件、看不到接管关系、拿不到失败原因。于是凡是需要
判断「页面到哪了 / 我还能不能操作它」的地方，全部退化成猜测；**猜错就静默卡死，
而且卡死态会被状态工具描述成「排队中」**。

本版按 `issue-期望闭环需求与改动清单.md` 的 R1–R7 把 C1–C22 一次交付（一次装机即可验）。

### 1. 一份真相：`lib/capture-phase.js`

新增纯函数 `deriveCaptureView()`：插件工具、状态工具、队列小球、前端提示条**全部读它**。
"工具说 queued、面板说失败"的双源矛盾在结构上不再可能出现（C20）。

`armed` 分支三态化，禁止再折叠成 `queued`（C6）：

| 处境 | 旧行为 | 新行为 |
|---|---|---|
| 心跳过期（客户端 10s/60s 没上报） | `queued`（排队第 1 位） | **`heartbeat-lost`**（终态） |
| 壳显式交还（`lastPendingTaskId` + `releaseReason`） | `queued` | **`orphaned`**（终态） |
| 超过宽限期始终没人接管 | `queued`（永远等） | **`orphaned`**（终态） |
| 浏览器正忙着别的任务 | `queued` | `queued`（保留） |

三种终态都给 `requiresUserAction=true`、`nextAction=recreate-or-cancel`，以及
**「重建任务 / 终止任务」两个可执行选项**的 `question`（C7/R4.3）。心跳 TTL 按阶段分档
（下载/归档 60 秒，其余 10 秒，C13），"心跳超时（上次上报 N 秒前）"与"该任务未在此浏览器
打开（当前 pendingTaskId=…）"拆成两句不同的错误（C14）。

### 2. 页面驱动 + PDF 载荷（层 1：壳）

- **响应层取 PDF**（C1/R2.2/R5.1）：`WebResourceResponseReceived` + `GetContent` 把
  `application/pdf` 的响应体流式写到该任务**专属**的暂存文件（`*.payload.pdf`，与下载目标
  分开，避免两个写入者互相截断）。保存因此不再依赖 PDF 查看器的「另存为」界面，
  也不读、不导出任何 Cookie。
- **页面事件**（C2）：`SourceChanged` / `NavigationCompleted` 上报
  `url / documentType / httpStatus / readyState / contentLength`，并带单调递增的 `pageSeq`。
- **接管/交还显式化**（C3）：`lastPendingTaskId` / `releaseReason` / `takenOverAt`。
- **操作必须终态**（C4/R4.1）：`lab_browser_save_current_pdf` 等归档完成才返回——
  成功 `{path, bytes, sha256}`，失败给原因；**不再出现 `{started:true}` 之后失联**。
  保存类操作 TTL 30 秒 → 120 秒，过期把原因写回任务行（C15/C16）。
- **候选项加 `autoDownloadable`**（C12）：`?download=true` / 带 `download` 属性 / 直链文件
  为 true，点了会直接下载而不是只进预览器。

### 3. 工具（层 2/3）

| 工具 | 变化 |
|---|---|
| `lab_publisher_browser_capture_list` | **新增**（C10/R1.2）：列出课题全部捕获任务与阶段，找回丢失的 taskId |
| `..._download_cancel` | 新增 `recreate: true`（C11/R1.4）：用同一篇文献立刻重建，返回新 taskId，不用用户重新确认 |
| `..._download_status` | 输出 `page / pdf / heartbeat / alternateEntry / stalled / saveReady`；终态给重建/终止选项 |
| `lab_browser_wait` | 指纹加页面维度（C9）：旧指纹里导航不改变任何一项，页面跳了也报「没有变化」；已是终态则立即返回 |
| `lab_browser_save_current_pdf` | 等到终态（C4） |
| `lab_browser_operation_status` | 新增 `waitMs`，可在插件内等到终态 |

`automationStage=manual`（原生 PDF 无可用元素）不再返回那个会静默失败的动作名，
改为 `nextAction=retry-download-entry` + `alternateEntry`
（从 `/doi/epdf|reader/<doi>` 规范化出 `/doi/pdf/<doi>?download=true`，C8）。

### 4. 小球与提示条（层 4）

小球文案/色调直接取插件推导结果（C20）；`saving` 增加停滞分支（60 秒无字节增长 →
`tone:"error"`，C17）；`manual` 文案改成可执行指引（C18）；失去接管时小球出现
**「重建」**按钮（C19）。另外修掉一个实际卡顿：客户端以前**内联 await** 浏览器动作，
保存 PDF 的几十秒里整个 1.8 秒轮询被卡住、队列快照不再上报——动作改到独立任务里跑。

### 5. 预设（层 5）

不再教「落到原生 PDF 就调保存工具」；只有 `nextAction=save-pdf-ready` 才调，
`retry-download-entry` 时改用 `alternateEntry`，终态时用 `recreate=true` 重建（C21/C22）。

### 6. 顺带修掉一个会弹模态框的探测缺陷

`runtime/deps.rs` 的依赖探测对捆绑 `node.exe` 直接 `Command::new()`。当文件不是有效 PE
（安装不完整、被安全软件截断）时，Windows 不返回错误码，而是弹
**「不支持的 16 位应用程序」**模态框并挡住整个探测——提示与病因毫无关系。
现在先检查文件头（`MZ` + 合理体积），不满足就如实报「安装文件不完整或被安全软件截断」。
单元测试的沙箱假 `node.exe` 也因此不再交给系统执行（那个测试此前要跑 5 分钟以上，
现在 0.4 秒）。

- **动作延迟**：浏览器的 observe/click 仍要等客户端 1.8 秒的轮询节拍去领取操作。
  计划改成 `browser_operation_claim` 长轮询 + 专门的即时动作循环（beta12 起排队）。
- 八家出版社的 iWAN 标定仍全为 `pending`（`docs/PUBLISHER_DOWNLOAD_CALIBRATION.json`），
  需要人工在真机 iWAN 环境里逐家验收；**本轮不声称已完成**。
- issue.md 的 B3（网络中断有限次重试）、B5（重启失效任务的 UI 区分）、B7/O6/O7、O4。
