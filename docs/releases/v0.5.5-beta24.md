# v0.5.5-beta24 发布说明

发布日期：2026-09-29

## 主题：不再模拟按键，改为在 WebView2 自己的网络会话里把 PDF 读出来

β21–β23 一直在修"给原生 PDF 查看器发 Ctrl+S"这条路：焦点被 Windows 前台锁挡住、按键没产生下载、
100 秒空等……这些都是**方法本身**带来的问题。这一版把方法换掉了。

### 现在怎么取字节

保存工具（以及页内浮层）现在通过 **WebView2 自己的 CDP** 重新读取当前 PDF：

1. `Page.getFrameTree` 找到主 frame；
2. `Network.loadNetworkResource` 带 `includeCredentials: true` 在**浏览器自己的会话里**重新加载该 URL
   —— 用的就是查看器已经认证过的那个会话，**不读取、不导出、不记录任何 Cookie 或签名 URL**
   （响应头里只取 `content-length`，日志行不带 URL）；
3. `IO.read` 按 256 KiB 分块流式写入**任务专属暂存文件**（支持 base64），上限 100 MB，
   任何路径都会 `IO.close`；
4. 收到的字节数必须**等于响应声明的 `content-length`**；文件必须真的是 PDF
   （`%PDF-` 头 ∧ 尾部 `%%EOF` ∧ ≥ 8 KiB）；
5. 通过校验后才交给既有的归档通路（与下载事件那条路同一个上传/登记实现）。

**要求 `success && httpStatusCode == 200`**：重定向、错误页、分段资源都不可能被误当成正文。

失败时不装死：`abort_direct_pdf_transfer` 释放任务目标（清认领、回到 waiting-download、删掉半截文件），
这样**人工按 Ctrl+S 仍能被下载事件捕获**，错误信息里也直接这么写。

### 随之删除的东西

`SendInput`、`VK_*`、`SetForegroundWindow`/`GetForegroundWindow`、以及基于 `SaveAsUIShowing`
的查看器保存路径**全部移除**，`windows` crate 的
`Win32_UI_Input_KeyboardAndMouse` / `Win32_UI_WindowsAndMessaging` 两个 feature 一并去掉；
新增 `base64`（用于 CDP 流）。

## 为什么这次更可能一次成功

前面几版的失败都发生在"让浏览器自己保存"这条**间接**路径上（焦点、按键、查看器 UI、另存为对话框）。
现在拿到的是 **HTTP 200 的完整响应体**，并且**逐项校验**（状态码、声明长度、实际长度、PDF 头尾、体积），
任何一项不符都不会进归档——要么成功，要么给出确切原因。

## 真机验收

1. **原生 PDF**：进 PDF → 调保存（或点右下角浮层）→ 期望日志出现
   `directPdfFetch … 已在 WebView2 网络会话内发起当前 PDF 读取`，紧跟
   `PDF 已完整写入任务暂存文件（N 字节）`，然后 `captureCompleted`；`N` 应与页面标称大小一致。
2. 若出现 `PDF 网络读取失败：…`：请把那行原文给我——说明该站的 PDF 是**一次性签名 URL**
   （重取会失效），那就得回到响应层/下载事件那条路，我需要知道是这种情况。
3. **人工兜底**仍有效：在侧栏 PDF 上按 Ctrl+S，下载事件会捕获并归档。
