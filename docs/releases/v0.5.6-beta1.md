# v0.5.6-beta1 发布说明（候选版本）

> 这是 **0.5.7 需求集的候选构建**：按
> [`docs/0.5.7_LITERATURE_CAPTURE_REQUIREMENTS.md`](../0.5.7_LITERATURE_CAPTURE_REQUIREMENTS.md)
> 的"0.5.7 批次"实施。上一稳定版为 `v0.5.6`（说明见 `v0.5.6.md`）。
> 本文件在产物构建完成后补上校验值；**每条状态只按实际验证过的范围写**。

## 一、这一版改了什么

### 1. 正文只有两条来路（R2）

实机确认两条通路后，把第三条退役：

| 页面形态 | 通路 | 落盘 |
| --- | --- | --- |
| 出版社定制 PDF 预览页 | 点页面上的下载控件 → 浏览器**下载事件** | `<taskId>-<kind>.pdf` |
| 浏览器默认 PDF 查看器 | CDP `Fetch.requestPaused`（Response）取原始正文 | `<taskId>-<kind>.payload.pdf` |
| 其余（直链、`?download=true`、附件响应） | 同为下载事件 | `<taskId>-<kind>.pdf` |

**退役的是** `WebResourceResponseReceived` + `GetContent` 的响应层取体（旧通路 B），
连同它独有的 `206 / Content-Range` 分段装配与一段必须跨线程封送的 COM 流读取代码
（历史上"一进原生 PDF 页就崩溃"的双重 Release 就出在那里）。

**保留的是** 同一条 WebView2 事件里的**事实上报**：`content-type / content-length / status`
仍然由它给出——`documentType`、`httpStatus`、`contentLength` 与"顶层是不是 PDF 文档"的判定
都依赖这个。

**必须明说的代价**：`206` 分段不再装配。若某站点只给 Range、不给整份响应，正文只能从
下载入口取（换 `download=true` 一类入口）。这条已写进手册的"已知限制"。

### 2. 归档不再静默覆盖（R3）

- **建任务前预检**：条目已归档同类型文件时**不建任务**，工具直接返回
  `already-archived` + `archiveConflict` + 让用户三选一（替换 / 保留 / 取消）的问题；
- **归档端点二次硬校验**：写入前检查目标是否存在或已登记，未获授权 → **HTTP 409
  `already-archived`**，原文件一个字节都不动；
- **覆盖是人类决策**：任务行新增 `allowOverwrite`（默认 `false`），只有在用户明确选择
  "替换"后才由 `replaceExisting=true` 置真；
- **旧版本留证**：确认替换时旧文件改名 `<stem>.previous-<sha8>.<ext>` 保留一份，
  provenance 记明"这份替换了谁"；
- **小球显示「已有文件」**：`ballState=conflict`，文案以「已有文件：」开头，
  而不是又一条需要读第二遍的"下载失败"。任务结束、pending 已经交还之后，
  小球仍会沿用**插件推导的那句话**（`ballText`/`ballTone` 随 notice 一起下发），
  不再退回壳按 state 猜出来的"下载或归档失败，请重试"。

### 3. 失败原因成表（R4）

`reasonCode` 成为机器可读的固定取值（`already-archived` / `kind-mismatch` /
`missing-pdf-header` / `missing-eof` / `payload-too-small` / `too-large` /
`token-invalid` / `token-replayed` / `task-not-armed` / `task-expired` /
`transfer-incomplete` / `upload-failed`），HTTP 状态由 code 判定，不再靠中文字符串匹配——
文案一改状态码就漂的日子结束了。

### 4. 关窗即终止（R9，Phase A）

**这是一个真实漏洞的修复**：壳上报的 `pendingTaskId` 与插件侧的"被持有"判定
**都不看 `windowOpen`**。用户关掉文献浏览器之后，任务仍被判为"被这个浏览器持有"，
阶段停在壳最后报的状态，Agent 只能一直等一个永远不会到来的变化。

现在：`windowOpen=false` ⇒ 壳释放 pending（写入 `releaseReason`）⇒ 插件派生终态
**`window-closed`**，任务终止，已下载的文件仍留在本地，`nextAction=recreate-or-cancel`
并给出"重建（会重新打开浏览器）/ 清理"两条路。

### 5. 错误码与文档（R4/R13）

- 手册 `docs/LITERATURE_DOWNLOAD_CHAIN.md` 改为 **A/C 两条通路**，补充 `reasonCode` 表、
  `window-closed` 阶段、`ballState` 展示态、`.notpdf.bin` 取证位置，并删掉**已不存在的
  `mode` 参数行**（现工具参数为 `bundleId/kind/projectId/loginConfirmed/replaceExisting`）；
- 标定文件 `docs/PUBLISHER_DOWNLOAD_CALIBRATION.json` 新增 `capturePaths`，把两条通路
  记为 `verified: real-device`，并把已退役的通路写进 `retired`；
  **逐社状态一律保持 `pending`**——确认的是通路，不是任何一家出版社的机构会话。

### 6. 双模式边界固化（R6）

面板发起的任务（`requestedBy=user`，即 human 模式）**拒绝一切自动化浏览器动作**
这条硬约束本来就存在，本版补上了针对性回归测试（observe / click / viewer-download
三条动作 × human 任务 = 全部被拒）。

## 二、明确未做的事

按需求书 §10 的分批，本版**只做 0.5.7 批次**。以下仍未实施，请勿当成已支持：

- **R1 OA 优先策略**（闭源直走机构、只对已知 OA 社探测）：未实现，决策已记入需求书；
- **R5 分件删除**（只删 PDF / SI / 精读报告 / PPT）：未实现；
- **R10 小球完整 5 态视觉收敛**：本版只提供 `ballState` 与「已有文件」文案；
- **R11 无固定等待**（`lab_browser_wait` 上限 20 s → 120 s）：未调整；
- **R12 多任务多窗口并行**：只做了 Phase A（关窗即终止），多窗口未动；
- **R7 人工点击轨迹 / R8 规则确认对话框**：未实现。

另外三条边界必须说清楚：

1. **通路 D（WebView2 原生另存为）暂未退役**，仍是载荷未就绪时的兜底——需求书 §11 Q3
   等你裁定；
2. **没有做任何出版社的机构会话标定**：八家的 `authenticatedIwanVerification` 仍全是
   `pending`，本版只把"正文怎么拿到"这条通路的机制记为真机确认；
3. **iWAN 真机视觉验收仍未做**：0.5.6 的 42 px 导航栏与底部归档按钮没有在你的页面上目视确认过。

## 四、装机后建议确认四件事

1. 打开一篇**浏览器原生 PDF**：日志应出现 `pdfFetch` 的"已捕获原请求 PDF（N 字节），载荷已就绪"，
   随后自动归档；期间不应再出现任何 `GetContent` 相关记录；
2. 打开一篇**出版社 HTML 预览页**：点页面上的下载控件，走下载事件归档；
3. 对**已归档过正文**的条目再发起一次 pdf 捕获：应在**建任务前**就被拦下并给出
   "替换 / 保留"的选择；强行走到归档也必须失败且原文件未被改动；
4. 捕获进行中**关掉文献浏览器**：状态应在 1–2 秒内变成 `window-closed`，
   不再显示"正在等待"。
