# v0.5.5-beta21 发布说明

发布日期：2026-09-28

## 主题：让预览页自己的保存/下载真正可用

beta20 的反馈很直接：**不再产出 1 KB 了，但依然下不完**，而且要求明确——"想办法让 AI 能点预览页工具栏的保存"。
这一版就按这个方向做。

### 1. 原生 PDF 查看器：让查看器自己保存（Ctrl+S）

原生查看器的工具栏**不在文档 DOM 里**（脚本注入不到，所以 `observe` 永远是 `candidates: []`）。
`ShowSaveAsUI` 又只保存**顶层 HTML 壳**——这正是先前"1 KB"的来源。现在改走**查看器自身的保存动作**：

- 保存工具与页内「下载并归档 PDF」按钮都走 `download-viewer-pdf`；
- 先聚焦主窗口与子 WebView，**确认前台窗口属于本进程**（否则直接放弃，避免快捷键打到别的应用），
  再发送 Ctrl+S；
- 查看器的保存变成一次**普通下载**，落到任务自己的暂存路径 → 由**已经验证过的下载通路**归档；
- 若查看器走的是"另存为"对话框，已注册的 `SaveAsUIShowing` 处理器把路径直接设成任务暂存路径
  （`SetAllowReplace(true)`，允许同一任务重试覆盖自己未完成的文件），不弹对话框；
- 响应层已经拿到**完整载荷**时仍然直接归档，不必再触发查看器。

进度只在查看器保存进行中、且顶层是 200 的 `application/pdf` 文档时才给出 `downloadTotalBytes`
（取该文档的 content-length），**不在别处编造总量**。

### 2. 出版社 HTML 预览页：不再无限等待，回去点真实入口

出版社预览页的 Download 按钮**是在 DOM 里的**，本来就是可靠路径（历史日志里所有
`downloadRequested → captureCompleted` 成功案例都来自它）。所以当响应层只拿到 HTML 壳或分段碎片时：

- 状态不再停在"正在接收"等到天荒地老，而是回到 **`observe-or-click`**，让 Agent 去观察并点击真实入口；
- `progress.source` 区分 `browser-download` 与 `viewer-buffer`，下载进度**只算浏览器真正写入的字节**；
- 等待消息变成"浏览器正在下载…（已写入 X / 共 Y，Z%；N 秒未增长）"，未知总量时明说"总量未知"。

### 3. 页内浮层的措辞与启用条件

查看器还没加载到 PDF 时，浮层不再提供"保存"（那是点不通的），而是显示
**「请点击页面的 Download PDF」**；只有在 `documentType=application/pdf` 或载荷已完整时，它才可点。

## 真机验收（按这个顺序）

1. **原生查看器**：进原生 PDF 后调一次保存（或点右下角浮层）→ 期望查看器自己弹出/静默完成保存 →
   任务 `completed` 且字节数与页面标称一致。日志里应看到 `downloadRequested` 紧跟 `captureCompleted`。
2. **出版社 HTML 预览页**（Wiley `aiche.../doi/epdf/...`）：状态**不应**再停在"正在接收"；
   应给 `observe-or-click` → `observe(scope=all)` 找到页面自己的 `Download PDF` → 点它 →
   走下载通路归档。
3. **工具栏让位**：我们那条 76 px 工具栏现在可收起（左上角把手展开），出版社自己右上角的按钮
   应可点。
4. 若第 2 条里 `observe` 找不到任何 Download 入口，请把该页面的 `observe` 原始返回发我——
   那说明该站的入口在**跨源 iframe** 里，需要另一种注入方式。

**仍未验证**：各出版社的入口形态（DOM 工具栏 / 跨源 iframe / 原生查看器）需要逐站真机确认；
八家出版社的机构会话标定全部仍为 `pending`。
