# v0.5.5-beta1 发布说明

发布日期：待定

## 主要更新

本版来自 0.5.4 的**真实试用复盘**：一位 Agent 用 0.5.4 完整跑了一遍「文献检索 → 精读 →
PPT 汇报」的真实任务，并交回了耗时/token 归因与七条问题。本版逐条修掉，并把「Agent 应该用
哪个运行时、怎么核对成品」从"靠猜"变成"可查询的事实源"。

---

### 1. Agent 运行时环境：优先用软件自带的，而不是宿主机的

试用现场的两条根因：① 桌面壳只导出了 `IBM_LAB_AGENT_BUNDLED_PYTHON`，没导出 node，子进程
PATH 里也只有 Python 目录 —— Agent 只能硬编码 `C:\Program Files\iBM Lab Agent\node\node.exe`；
② LibreOffice 的 user profile 落在 `%LOCALAPPDATA%\Temp`（桌面壳沙箱拒绝写）时**静默不产出
PDF**、退出码仍是 0，白耗好几轮才定位。

- **桌面壳**（`desktop/src-tauri/src/runtime/`）：子进程 PATH 现在预置捆绑 **Python 与 Node**
  两个目录；新增导出 `IBM_LAB_AGENT_BUNDLED_NODE`；`TMP`/`TEMP`/`TMPDIR` 全部指向工作区内的
  `.lab-tmp` 并预建（Python 的 `tempfile` 只在目录存在时才认 `TMPDIR`，否则静默回退 `/tmp`）。
- **统一解析器** `src/lab-runtime.js`：捆绑 → 本进程自身（DSH 就跑在壳启动的 node 上）→
  系统 PATH（需显式允许）。顺带修掉一个真实陷阱：`pythonCandidates` 的 `command` 是**数组**
  （Windows 的 `py -3.12` 是多 token 前缀），当字符串用会直接把数组当命令。
- **Agent 工具 `lab_runtime_env`** + preset 第 17 条：返回 python/node/soffice 的绝对路径、
  `argv` spawn 前缀、工作区临时目录、渲染助手与体检器的**绝对路径**，并要求"先问不要猜、
  不要硬编码安装路径、不要写相对路径（Agent 的 cwd 是课题工作区，不是插件安装目录）"。
- LibreOffice **不由本仓库捆绑**（解析链是"显式配置 → 典型安装路径 → PATH"，与应用内预览同源）；
  本版把 profile 固定到工作区，并把"退出码 0 但没产出文件"显式报错。

### 2. 核对成品：零视觉 token 的路径

试用现场最贵的开销是**逐页读图自查**（25 次 `read_image`，约 15 次可省）。

- **渲染助手** `scripts/render-deck.mjs`（+ `scripts/pptx/pdf_to_png.py`）：pptx/pdf → 逐页 PNG，
  默认再合成一张 **contact sheet**，一次读图看完整套版面；profile 固定在工作区；失败模式明确
  （不再有"静默不产出"）。
- **成品体检器** `scripts/pptx/inspect_deck.py`：一次给出每页字体三槽（`a:latin`/`a:ea`/`a:cs`）、
  最小显式字号、图片是否被拉伸、形状是否越界、占位符是否仍是提示文字、段落是否带项目符号。
  **这些都不需要读图** —— 视觉 token 只留给"版面好不好看"。
  实测 `deck6.pptx`：4 页、最小显式字号 20.0pt、error 0 / warning 0、每页
  `latin=Arial ea=微软雅黑 cs=Arial`；负例自证会失败（`--min-font-pt 30` → 11 error 退出 1）。

细节见 [`docs/AGENT_RUNTIME_ENVIRONMENT.md`](../AGENT_RUNTIME_ENVIRONMENT.md)。

### 3. 试用复盘驱动的模板与工具修复

**① 笔记模板工具（`lib/templates-tool.js` / `lib/note-templates.js` / `lib/goal-profiles.js`）**

- `lab_note_templates_list` 的输出 schema 声明了 `additionalProperties: false` 却**漏声明 `kind`**，
  而服务返回的每一行都带 `kind`（note/review）→ 输出校验直接失败，Agent 只看到
  「templates[0].kind 未声明」，只能绕过工具去手读存储。补上并对同文件其余工具逐个核对
  （PPT list 的 7 个字段与 `labTemplates.list()` 逐字段对齐）。
- `resolve(id, version)` 只要 `version !== undefined` 就拼 `id@version`：Agent 传字面量 `"latest"`
  （错误文案本身也写成 `@latest`，进一步误导）就会去找 `note-default@latest`，永远找不到。
  改为 `"latest"` / 空串 / 纯空白一律当「未指定」；`lib/goal-profiles.js` 同源同修。
- not-found 现在带上该 id 的**实际版本列表**（archived 标注）与下一步提示。
- **刻意没改** `latestActive` 的"只看最新一行"语义：`delete` 就是追加一个 archived 的**更高**版本，
  向下找 active 会让已删除的模板复活，并直接打破既有的删除断言。这一条是并行工作流带证据
  **推翻了我的指示**，我复核代码与集成测试后确认它对。

**② builder 的 contain（`scripts/pptx/build_from_template.py`）**

- 原来 contain 分支**一行几何都不设**，全交给 `insert_picture()` —— 它不仅不写 `a:xfrm`，还会用
  `a:srcRect` 把图**裁**成占位符比例。实测 600×690 竖长图进 Fig3 的 12.85×4.78 in 槽位：

  | | 有效几何 |
  |---|---|
  | 修前 | 12.85×4.78 in，**上下各裁 33.8%**（图表内容丢失） |
  | 修后 | 4.15×4.78 in @(4.51,0.99)，比例与源图一致、严格在框内且居中 |

- 顺带查出**第二个更深**的缺陷：几何必须在 `insert_picture` **之前**读 —— 它会把占位符的
  `spPr/xfrm` 清掉，之后再读 `target.width` 抛 `AttributeError`。**原 cover 分支正是因此在真模板上
  从未生效**（静默降级 + 一条误报的"crop 不可用"warning）。cover 语义按约束未改（实测"复活"它
  会算出 12.85×14.78 in，比幻灯片还高）。

**③ 容量模型（`src/ppt-slot-spec.js` + `lib/pptx-plan.js`）**

- pptx-cli 的 `max_lines` 只按高度算、行距**硬编码 1.22 倍**、不读 `a:lnSpc` 与 `a:spcBef/a:spcAft`、
  也不把可用高度夹到版面下边界。本模板正文是**固定 30pt 行距 + 段前 10pt / 段后 14pt**，于是系统性高估：

  | 槽位 | pptx-cli | 自算 | 高估 |
  |---|---|---|---|
  | fig1/fig2/fig4 `analysis` | 19 行 | **15** | 27% |
  | abs `abstractZh` | 18 | 15 | 20% |
  | fig3 `analysis` | 4 | 3 | 33% |
  | end `innovation` | 7 | 6 | 17% |
  | end `paragraph1` / `paragraph2` | 4 / 4 | 3 / 3 | 33% |

- 现在由我们自算（模板真实行距/段间距 + 版面下边界夹取），并**接进了 slots.json 的两个写入方**。
  这一环最初漏了：模型改对了，但派生 slots.json 的导入流程与 `--write-slots` 没传 typography，
  落盘仍是默认模型（行距 1.2 倍、段间距 0），**自算值与 pptx-cli 完全一样（body_15 19 vs 19）**
  —— 单测全绿却在生产路径退化。已补 3 项回归测试（功能 + 负例 + **源码级接线断言**）锁住。
- **顶格也告警**：多行框 `estimated >= 容量` 即 warning（估算精度约 ±1 行），单行框只在真的超过时
  才告警（否则封面四槽 + 图注一页四条噪声）。这条是**渲染核对**发现的 —— 真实 5 页计划的成品
  第 4 页最后一行溢出到幻灯片外被裁，而编译器当时沉默。
- 派生链现在会给"排版解析不到"显式报警（`capacity-typography-unresolved`），不再静默退化成默认模型。

**④ 按图片真实比例选版式（`lib/pptx-plan.js`）**

- 只读 PNG/JPEG/GIF/BMP 文件头（不引依赖、不调 python），对候选版式的图片占位符算 contain 后的
  显示尺寸与留白，选**显示面积最大**者；门槛保守（≥1.15 倍、不丢已声明槽位、未被 `plan.roles` 钉住、
  未被 requiredPages 引用），否则只出建议并附候选对比。
- 实测 600×690 竖长图：**fig1** 显示 5.22×6.00 in（31.32 in²）> fig3 的 4.16×4.78 in
  （19.88 in²、留白 68%）→ 选 fig1，正是试用里"放进 Fig3 字小到看不清"的反例。
- 换版式加了**双向守卫**：目标版式的必填槽必须都已被声明，否则不换并把原因写进诊断。
  这条是我复核时发现的 —— 单向守卫会把"没声明图注"的合法计划换出 `required-slot-missing` 错误。

**⑤ 登记前置条件可见（`lib/tasks-tool.js`）**

`lab_tasks_register_presentation` 的 description 现在写明依赖链「登记原文 → 登记精读报告
（`lab_tasks_register_report` 返回 reportId）→ 登记 PPT」，并点明**公众号/题录元数据登记不会自动
生成精读报告**；`has no staged report artifact yet` 被翻译成可执行的下一步，其余错误原样透传。
