# v0.5.5-beta20 发布说明

发布日期：2026-09-28

## 主题：分段装配（两个 bug，一个根因）

### bug1｜Wiley 预览页永远"正在接收 4.4 MB"，且手动也存不了

`aiche.onlinelibrary.wiley.com/doi/10.1002/btm2.10616`。壳日志给出了答案——这份 PDF 是
**4,594,707 字节**，而浏览器的 PDF 查看器是用 **18 个 256 KiB 的 Range 请求**把它拉下来的：

```
bytes 0-262143/4594707 … bytes 262144-524287/4594707 … bytes 4456448-4594706/4594707
```

**β16 的那个决定是错的**：当时为了修"256 KiB 分片被当成整份文件"，我把所有 206 响应**一律跳过**
（日志里那句"分段不是整份文件，不能当载荷"）。而分段恰恰是**真实字节唯一出现的地方** ——
丢掉它们，载荷永远收不全、状态永远停在"正在接收"，保存只能退回查看器那条路。

现在改为**装配**：

- `PdfPayload` 记录**已覆盖区间**，每个响应按 `Content-Range` 的起始偏移**写到文件的对应位置**（稀疏写）；
- 完整 = 区间并集**从 0 连续覆盖到总长**；总长未知（chunked / `*`）时才要求读取器证明尾部 `%%EOF`；
- 只有**无法解析**的 `Content-Range` 才跳过，并且记日志；
- 多个响应同时写同一个载荷文件现在是**预期行为**（旧规则"只允许一个读取者"改成"完整后不再接受新段"）。

### bug2｜所有原生 PDF 预览界面，保存工具"始终是 1KB"

根因是上一个 bug 的下游：载荷拿不到 → 退回 `ShowSaveAsUI` → 而 **`ShowSaveAsUI` 保存的是"页面"**，
原生 PDF 的文档壳正是那段 348 字节的 HTML 查看器页面 → 于是把一个约 1 KB 的 HTML 当正文交上去。

现在 `viewer_saved_pdf_is_usable` 在**上传之前**验产物，判据与捕获服务一致
（`%PDF-` 头 ∧ 尾部 `%%EOF` ∧ ≥ 8 KiB），不合格就**删掉并给出确切原因**：

```
查看器保存得到的是页面（348 字节），不是 PDF；该站点的 PDF 需要从下载事件或响应体获取
```

—— 而不是把垃圾归档进条目。

### 顺带：工具栏可收起

我们那条 76 px 固定工具栏正好压在出版社预览器的保存按钮上（现场："右上角工具栏无法渲染出来"）。
现在它带一个**收起**按钮，收起后只留左上角一枚"展开工具栏"把手，host 高度归零、不再挡点击。
**没有**给出版社页面加任何 transform —— 那是早先白屏的成因，不再重犯。

## 真机验收

1. **原样复现 bug1**：`aiche.onlinelibrary.wiley.com/doi/10.1002/btm2.10616` 点 `PDF` 进预览页，
   等 `nextAction=save-pdf-ready`（载荷应显示 4.4 MB 收满）→ 调保存 → `completed` 且归档
   约 4,594,707 字节。日志里应看到 18 个 `Content-Range` 分段被接受，而不是"跳过"。
2. **bug2**：任一原生 PDF 预览界面调用保存，**不允许**再出现约 1 KB 的产物；
   若走查看器那条路，必须得到"查看器保存得到的是页面（N 字节），不是 PDF"这样的明确原因。
3. **工具栏收起**：点工具栏上的 ▲，页面顶部的出版社按钮应露出来并可点；左上角把手可展开。

**仍未验证**：其他出版社的 Range 行为（有的整份 200、有的分段）、以及八家出版社的机构会话
标定全部仍为 `pending`。
