## 3. P0：修复截图“显示成功”假阳性

涉及文件：

- `client/index.js`
- `tests/unit/synthesis-workspace-client.test.mjs`
- 新增真实浏览器测试

### 3.1 当前问题

`EvidenceShot` 创建 Object URL 后，探测图片的 `onload` 立即调用 `URL.revokeObjectURL(objectUrl)`，随后才通过 `setSrc(objectUrl)` 把同一地址交给实际 `<img>`。浏览器可能显示空白或加载失败，但代码已经设置 `state="ok"` 并调用 `onReady`。

这违反“用户实际看到右侧原文截图后，才能确认左侧事实”的要求。

### 3.2 修改要求

- 探测成功时不要立即释放 Object URL。
- 将新 URL 写入组件状态前，释放上一个不再使用的 URL。
- 组件卸载、Evidence 切换或重新加载时释放当前 URL。
- `onReady` 必须由实际展示图片的 `onLoad` 触发，而不是仅由隐藏 probe 触发。
- 实际 `<img>` 的 `onError` 必须撤销 ready 状态并调用 `onFailed`。
- 使用 `ref` 保存当前 Object URL，避免 effect cleanup 捕获旧 `src`。
- Evidence 快速切换时使用 `AbortController` 或请求序号，禁止旧请求覆盖新 Evidence 状态。

### 3.3 必测用例

- PNG 响应有效且实际 `<img>` 加载成功：才允许确认。
- HTTP 200 但正文不是图片：不得允许确认。
- URL 在实际 `<img>` 加载前失效：不得调用 `onReady`。
- Evidence A 请求晚于 Evidence B 返回：A 不得覆盖 B。
- 组件卸载后 Object URL 和 fetch 均正确清理。

## 4. P0：截图核验必须绑定当前原文位置

涉及文件：

- `src/synthesis/models.js`
- `lib/synthesis.js`
- `lib/evidence-shot.js`
- `tests/integration/synthesis-review-batches.test.mjs`
- `tests/unit/evidence-shot-handler.test.mjs`

### 4.1 当前问题

服务端门禁目前只判断 `shotVerification.status === "ready"`，没有验证该 ready 是否对应当前 Evidence 的：

- `bundleId/documentId`
- `page`
- `bbox`
- PDF 内容摘要

`shotVerification` 模型没有保存 bbox；Agent 批次更新 `page/bundleId/documentId/bbox` 时也会保留旧的 ready 状态。结果是用户可能用旧页截图确认新页内容。

### 4.2 数据模型要求

在 `shotVerification` 中增加稳定的定位快照，至少包含：

```text
status
bundleId
page
bbox
sourceDigest
renderedAt
error
```

建议统一计算 `locationDigest`：对规范化后的 `bundleId + page + bbox + sourceDigest` 计算摘要。门禁校验当前 Evidence 定位与核验快照完全一致。

### 4.3 状态失效要求

以下任一字段发生改变时，必须在同一服务端写事务中把原状态改为 `stale`：

- `bundleId`
- `documentId`
- `page`
- `bbox`
- 已归档 PDF 的内容摘要

适用入口包括人工更新、Agent 批次回写、Evidence 更新和原文重新归档。不得等用户再次打开截图端点后才发现失效。

`evidenceShotGate` 必须同时检查：

1. 状态为 `ready`；
2. `sourceDigest` 非空；
3. 当前 bundle/page/bbox 与核验快照相同；
4. 对可检查的归档文件，当前摘要仍相同。

### 4.4 必测用例

- ready 后修改 page，状态立即 stale。
- ready 后修改 bbox，状态立即 stale。
- ready 后替换 bundle/documentId，状态立即 stale。
- PDF 内容被替换，原确认不能锁定路线。
- stale 后重新成功渲染，才恢复 ready。
- 旧版无 bbox/摘要的 ready 数据按不可信数据迁移为 pending 或 stale，不能静默放行。

## 5. P0：锁定必须使用可信用户身份

涉及文件：

- `lib/remote.js`
- `lib/synthesis.js`
- Remote 注册/工具暴露配置
- 服务集成测试

### 5.1 当前问题

`synth_route_lock` 是普通 Remote 方法，任何能够调用它的调用者都会被服务端强制转换成 `by: "user"`；`lockRoute` 又把缺省身份视为 user。这只是改写字符串，不是可信授权。

### 5.2 修改要求

优先方案：

- 由桌面/UI 调用层创建不可伪造的用户动作上下文。
- 服务端从调用上下文读取 actor，不读取 request 中的 `by`。
- `actor.kind === "user"` 且来源为受信本地 UI 时才允许锁定。
- Agent 工具注册表完全不暴露锁定方法。

如果当前框架无法传递可信身份：

- 将锁定移出通用 Remote/Agent 网关，改为仅桌面本地命令或专用 loopback user-action 端点。
- 端点应具备会话令牌、同源校验和一次性用户动作证明。
- `lockRoute` 必须要求显式 actor；缺失 actor 默认拒绝，不能默认 user。

### 5.3 必测用例

- 缺失 actor：拒绝。
- `by="user"` 字符串伪造：拒绝。
- Agent/tool 调用：没有该方法或服务端拒绝。
- 可信 UI 用户动作：通过。
- 已锁定路线再次锁定保持幂等，但不能借幂等响应泄露授权旁路。

## 6. P0：发布脚本必须在 Git 异常时失败关闭

涉及文件：

- `desktop/scripts/build-windows-release.ps1`
- `tests/unit/windows-release-scripts.test.mjs`

### 6.1 当前问题

脚本读取 `git status --porcelain` 后没有检查 `$LASTEXITCODE`。当 Git 返回 `bad object HEAD` 时，标准输出可能为空，脚本会把损坏仓库当作干净仓库继续打包。

### 6.2 修改要求

发布预检必须依次验证：

1. Git 命令存在。
2. 当前目录属于正常非 bare 仓库。
3. `HEAD` 可以解析为 commit。
4. `git status --porcelain` 返回码为 0。
5. `git diff --check` 返回码为 0。
6. 非 `AllowDirty` 模式下工作区为空。
7. 当前提交可以通过 `git fsck --connectivity-only`。

任何命令非零都必须立即终止，不得把空 stdout 解释为成功。

`AllowDirty` 只能用于诊断构建，并且：

- `release-report.json` 的 `publishable` 必须为 false。
- 安装包文件名或输出目录必须清晰标注 diagnostic。
- 后续“发布/上传”步骤必须拒绝该产物。

### 6.3 必测用例

- 模拟 `git status` 返回 128 且 stdout 为空：预检失败。
- HEAD 指向缺失对象：预检失败。
- dirty + 无 `AllowDirty`：失败。
- dirty + `AllowDirty`：仅允许诊断构建且不可发布。
- 干净、完整仓库：通过。

## 8. P1：消除截图状态写入竞态

涉及文件：`lib/evidence-shot.js`、截图服务测试。

### 8.1 当前问题

`recordShot` 返回异步 Promise，但调用处没有 `await`。服务可能先返回 PNG，再完成 `ready` 写入；用户快速确认时会遇到状态尚未持久化。异步拒绝也不会被同步 `try/catch` 捕获。

### 8.2 修改要求

- 将 `recordShot` 声明为 `async` 并等待持久化完成。
- 成功响应 PNG 前必须完成 ready 登记。
- failed/stale 登记也应等待，确保 UI 随后的查询能看到一致状态。
- 登记失败时不得伪装为核验成功；返回明确 5xx 或保持不可确认状态。
- 对同一 Evidence 的并发请求增加版本/定位条件，避免旧请求晚写覆盖新定位状态。

## 9. P1：修复 prepare-runtime 的事务切换

涉及文件：

- `desktop/scripts/prepare-runtime.ps1`
- `tests/unit/windows-release-scripts.test.mjs`
- 新增 PowerShell 故障注入测试

### 9.1 当前问题

node、dsh、plugin 逐项执行“正式目录移至备份、staged 移入正式目录”。如果后一个组件失败，前一个组件已经替换，脚本不会恢复；因此当前实现不是跨组件原子切换。

此外，备份目标目录在 `Move-Item` 前被创建，Windows 下可能把正式目录嵌套到备份目录中，导致恢复路径不确定。

### 9.2 修改要求

- 备份父目录可以预建，但每个组件的最终备份目标必须不存在。
- 记录每个已经完成的移动动作。
- 任一步失败时按相反顺序回滚：
  1. 将已安装的新目录移回 staged/quarantine；
  2. 将旧目录从备份恢复到原位置；
  3. 验证正式快照仍可用；
  4. 保留失败日志并清理本次 staged。
- 状态文件只能在所有组件切换并验证成功后更新。
- 定义备份保留数量或有效期，防止长期积累大型 runtime 树。

### 9.3 必测用例

- node 切换成功、dsh 切换失败：node 自动恢复。
- dsh 切换成功、plugin 切换失败：node/dsh 均恢复。
- 被终止后下次运行能够识别未完成事务并恢复。
- 热构建无变化时不复制任何组件，并在 30 秒内结束。

## 10. P1：统一 Ketcher 分阶段超时

涉及文件：

- `client/index.js`
- `scripts/ketcher-shell/src/main.tsx`
- Ketcher 浏览器测试

### 10.1 当前问题

宿主整单默认超时为 30 秒，而 iframe 内载入和导出分别最多允许 15 秒和 20 秒。合法任务可能在 30 至 35 秒之间完成，却被宿主提前判为失败。

### 10.2 修改要求

- 不再用一个短于所有子阶段之和的整单计时器覆盖阶段计时器。
- 推荐让 iframe 回传 `loading/rendering/exporting` 阶段消息，宿主按阶段重置对应超时。
- 如果保留总超时，必须大于初始化、载入和导出最大耗时之和，并预留通信余量。
- 超时或 `image:error` 后彻底删除 pending 项、取消计时器并继续队列。
- 失败任务不得写入缓存。

## 11. P2：限制 PDF 截图渲染进程

涉及文件：`lib/evidence-shot.js`、截图服务测试。

### 11.1 修改要求

- 为 Python/fitz 子进程设置明确超时，建议默认 30 至 60 秒并可配置。
